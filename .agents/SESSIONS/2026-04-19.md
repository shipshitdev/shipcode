## Session 6 — Fix: Pipelines auto-start on project import

**Status:** Complete

### Context

Bug report: importing the meterbar project caused 3 pipelines to auto-start without user action. Screenshot showed "[SSOT Migration] Import local task/prd" for 3 issues.

### Root Cause

Two contributing factors:

1. **Stale `queued` status survives project archival** — When a project is archived, its `github_issue_cache` rows keep their `pipeline_status`. When re-imported via `projects.add()`, the project row is un-archived but stale `queued` issues become live again.

2. **`getNextQueued()` has no project-archived filter** — The global queue drain query (`SELECT * FROM github_issue_cache WHERE pipeline_status = 'queued'`) scans all projects regardless of archived status. The startup drain loop (`index.ts:431`) or any `onPipelineTerminal` call picks them up.

### System Flow

```
User imports project (project:add)
         |
         v
  projects.add(path) finds existing archived row
  → UPDATE projects SET archived = 0
  → [BUG] stale queued issues now live again
         |
         v
  Startup drain (setTimeout at index.ts:431)
  → onPipelineTerminal() × maxConcurrentPipelines
  → getNextQueued() finds stale queued issues (no project filter)
  → pipeline.startFromGitHubIssue() — 3 pipelines auto-start
```

### What Was Done

- [x] **`projects.ts` — `add()` reset**: After un-archiving a project, reset all unclaimed `queued` issues for that project to `todo`
- [x] **`projects.ts` — `unarchive()` reset**: Same stale-state reset on explicit un-archive
- [x] **`github-issues.ts` — `getNextQueued()` JOIN**: Added `JOIN projects p ON p.id = gic.project_id` with `AND p.archived = 0` filter (defense-in-depth)
- [x] **3 new tests**: `add()` resets queued on restore, `unarchive()` resets queued, `getNextQueued()` skips archived projects

### Key Decisions

| Decision | Rationale |
|----------|-----------|
| Reset queued → todo on restore, not delete issues | Preserves issue cache; user can re-trigger manually |
| `AND claimed_at IS NULL` guard on reset | Never touch issues actively mid-pipeline |
| JOIN in `getNextQueued()` as defense-in-depth | Catches any code path that un-archives without the reset |
| Did NOT reset all queued on startup (Approach C rejected) | Would silently discard deliberate user queue intent; breaks crash recovery |

### Files Changed

- `packages/db/src/queries/projects.ts` — `add()` and `unarchive()` now reset stale queued issues
- `packages/db/src/queries/github-issues.ts` — `getNextQueued()` JOINs against projects, filters archived
- `packages/db/src/queries/projects.test.ts` — 2 new tests (add restore + unarchive reset)
- `packages/db/src/queries/github-issues.test.ts` — 1 new test (getNextQueued skips archived)

## Session 13 — Smart Retry + Failure Tracking

**Status:** Implementation complete, not yet committed

### Context

Issue #1 ("[EPIC] status.shipshit.dev — Uptime Monitor") failed 9 plans across 4 threads. Investigation revealed all 9 plans parsed successfully (`structured IS NOT NULL`). The "no structured plan was produced" error came from the latest sub-attempt where Codex/gpt-5.4 crashed instantly (exit code 1). The retry logic only checked the absolute latest plan — if that one had no structured content, it restarted planning from scratch, ignoring valid earlier plans.

### System Flow — Smart Retry Cascading Lookup

```
pipeline:retry triggered
         |
         v
  Get latest plan for thread
         |
  [Has structured?] ── Yes ──→ Use getRetryAction() → re-enter at correct phase
         |
        No
         |
         v
  plans.getLatestStructured(threadId)  ← walk thread backward
         |
  [Found?] ── Yes ──→ Clone into current thread → force review
         |
        No
         |
         v
  plans.getLatestStructuredForIssue(projectId, issueNumber)  ← cross-thread
         |
  [Found?] ── Yes ──→ Clone into current thread → force review
         |
        No
         |
         v
  Restart planning from scratch (existing flow)
```

### System Flow — Failure Phase Tracking

```
Pipeline enters phase (e.g. 'executing')
  → emitPhase(threadId, 'executing')
  → thread.status = 'executing'
         |
     [Phase fails]
         |
         v
  emitPhase(threadId, 'failed', error)
  → READ thread.status BEFORE write  ← captures 'executing'
  → recordFailure(threadId, 'executing', error)
  → Atomically: status='failed', failure_phase='executing', failure_count++
```
