## Session 4 — Instant Codex Terminal Render Loop Fix

**Status:** Complete (targeted fix verified; desktop typecheck later confirmed green)

### Context

Opening an instant Codex terminal crashed the renderer with:

- `Maximum update depth exceeded`
- component stack rooted at `InstantTerminalPane`

The failing path was the live instant terminal pane, not the drawer transcript. The symptom matched a `useSyncExternalStore` / Zustand selector returning a fresh value on every render.

### Root Cause

`InstantTerminalPane` subscribed to:

- `s.canonicalTerminalStream[threadId] ?? []`

That `[]` fallback created a new array on every render when a live terminal had not emitted any canonical events yet. React treated the snapshot as changed every time, which produced the infinite re-render loop when opening a fresh live pane.

### What Was Done

- [x] Replaced the inline `[]` fallback in `InstantTerminalPane` with a module-level stable `EMPTY_STREAM`
- [x] Added a regression test that renders a live instant pane with no stream data and verifies it mounts cleanly
- [x] Re-ran the nearby instant terminal session test to confirm restart/session behavior still works

### Files Changed

## Session 6 — Draggable Kanban Cards Were Swallowing Issue Selection

**Status:** Complete (root cause fixed; targeted UI + desktop tests green)

### Context

After the instant-terminal render-loop fix, issue detail still only opened reliably for the actively running planning card.

Observed symptom in the live board:

- `planning` card selection worked
- `queued` / `failed` / other draggable cards did not open Issue Detail reliably

### Root Cause

This was not an `IssueDetail` status gate.

The actual difference was:

- `planning` cards are **not draggable**
- `queued`, `failed`, `awaiting_approval`, `completed`, and `todo` cards **are draggable**

`KanbanBoard` was using dnd-kit with the default pointer activation behavior, so a plain click on a draggable card was being interpreted as an immediate drag start. In practice that prevented normal click-to-select behavior from landing cleanly on those cards.

### What Was Done

- [x] Added explicit dnd-kit sensors in `KanbanBoard`
- [x] Added a `PointerSensor` activation threshold of `distance: 8`
- [x] Kept keyboard dragging enabled via `KeyboardSensor`
- [x] Added a regression test that asserts the board uses a pointer movement threshold so draggable cards remain clickable
