### Key Decisions

| Decision | Rationale |
|----------|-----------|
| `queueMicrotask` for registry deletion, not synchronous | Sync listeners on `exit` may still want to read `manager.get(id)` to inspect `exitCode`/`state`. Defer one tick → both work. |
| `killAllAndWait` with SIGHUP first, SIGKILL after 5s | claude/codex want a chance to flush; but a wedged pty must not block app shutdown. 5s + 1s post-SIGKILL cap matches typical Electron quit budgets. |
| Always `event.preventDefault()` in before-quit, then `app.exit(0)` | `app.quit()` re-triggers before-quit; `app.exit(0)` is synchronous and bypasses the handler. `killInFlight` guard handles edge case where prior code path called `app.quit()` again. |
| Skip auto-cleanup of worktrees on quit | Worktrees are intentionally thread-scoped per `.agents/memory/worktrees.md`. Auto-cleanup would orphan threads. |
| Preserve `terminalThreadId` only when issue is null | When user switches issues, console should follow. When user closes detail, console should stay where it was so output is still readable. |
| Move `TerminalDrawer` outside `OverlayPanel`'s relative container | `OverlayPanel` uses `absolute inset-y-0` which spans its parent. Putting the terminal as a sibling rather than inside the same parent is the minimal restructure that achieves Cursor-like behavior. |
| File post-hoc tracking issues for completed fixes | Pre-release repo, no PR review process yet. Issues serve as audit trail. |

## Session 4 — Console layout v2: detail panel as row-level sibling (Cursor-style flanking)

**Status:** Complete. Layout change rode along with commit `f531cb2`. All 306 desktop tests green.

### Context

Vincent shared two new screenshots comparing ShipCode's console to Cursor's terminal. Session 1's earlier fix made the terminal full content-width (sibling of upper region), but the right detail panel was still nested inside the center column as an `absolute` overlay — terminal extended UNDER the detail panel horizontally. Vincent's ask: "the console in shipcode should be like in cursor. BETWEEN the sidebars. not above or below it. resize the console WHEN sidebars are open." → terminal must be flanked by both the left sidebar AND the right detail panel, resizing live as either flank toggles.

### System Flow

```
Session 1 layout (full-width terminal — still extended under detail overlay)
┌──────┬───────────────────────────────────┐
│ Side │ ┌────────┬───────────────┐        │
│ bar  │ │ views  │ IssueDetail   │        │
│      │ │        │ (absolute)    │        │

│      ├───────────────────────────────────┤
│      │ TerminalDrawer (full content w)   │ ← extends under detail
└──────┴───────────────────────────────────┘

Session 4 layout (detail panel = row sibling)
┌──────┬─────────────────────────┬─────────┐
│ Side │ views                   │ Issue   │
│ bar  ├─────────────────────────┤ Detail  │
│      │ TerminalDrawer          │ (col)   │
│      │ (between sidebar &      │         │
│      │  detail)                │         │
└──────┴─────────────────────────┴─────────┘
```

### Root Cause

`apps/desktop/src/renderer/App.tsx` rendered the right detail panel as an `absolute inset-y-0` `OverlayPanel` scoped to the upper region only. Even after Session 1 promoted the terminal to a sibling of the upper region (full content width), the detail panel stayed nested INSIDE the center column → terminal extended under it horizontally.

### Fix

Promote the detail panel out of the center column to row-level: `[sidebar | center | detail]` as flex siblings. Center column = main view + terminal. Right detail panel = sibling div with `data-slot="overlay-panel"` (matches existing test selector) styled as a docked column with `flex-shrink-0`, explicit `width` style, left-edge resize handle. `OverlayPanel` import dropped because the docked use-case wants normal flex flow, not absolute positioning.

### Context

User opened Project Settings on a renamed GitHub repo (`Gateway-Ventures/vitay-remastered` → `Gateway-Ventures/veref.work.git` on disk per `git remote -v`). Screenshot raised two complaints:

1. Renamed the repo on GitHub but ShipCode's `Git remote` row still showed the stale URL with no in-app way to fix it.
2. The `Default branch` row was static text, even though the Kanban toolbar already has a Local/Remote dropdown for the same field.

My first answer suggested running `git remote set-url origin …` on disk. User correctly pushed back: *"if we save the value, we could have a button to refresh it."* That reframing drove the design.

### System Flow

```text
Project Settings opens
    │
    ▼
useQuery ['git-branches', projectId] (fetch:false) → cached branch list
    │
    ▼
General tab renders:
  Git remote   [stale URL]                  [RefreshCw icon] ──► refreshGitRemoteMutation
  Default br.  [Select Local|Remote groups] [RefreshCw icon] ──► setDefaultBranchMutation
                                                              │  refreshBranchesMutation
                                                              ▼
                                                       IPC handlers
    │                                               (project:refresh-git-remote NEW,
    │                                                project:set-default-branch reuse,
    │                                                git:list-branches reuse)
    ▼
GitService.getRemoteUrl()  ──►  ProjectQueries.updateGitRemote()
                                       │
                                       ▼
                            invalidateQueries(['project',id], ['thread-panel-data',id])
                                       │
                                       ▼
                                fresh remote + selected branch in UI
```

### Affected Components

- **Frontend (renderer):** `ProjectSettingsModal.tsx` (added `git-branches` query + 3 mutations); `ProjectSettingsGeneralTab.tsx` (new props, RefreshCw button next to remote, `Select` for default branch); `ProjectSettingsLeafTabs.test.tsx` (prop fixtures).

- **Data:** `packages/db/src/queries/projects.ts` (new `updateGitRemote`); `packages/shared/src/ipc-channels.ts` (new channel).

### What Was Done

- [x] IPC channel + handler: `project:refresh-git-remote` re-reads origin via `GitService.getRemoteUrl`, persists when changed, returns `{ project, remote, changed }`.
- [x] Modal: `git-branches` query (`fetch:false`) + 3 mutations (`refreshGitRemoteMutation`, `setDefaultBranchMutation`, `refreshBranchesMutation`).

### Key Decisions (specific to this session)

| Decision | Rationale |
|----------|-----------|
| `project:refresh-git-remote` returns `{ project, remote, changed }` not just `Project` | `changed` lets callers later surface "no drift" feedback or auto-detect-on-open without an extra read. Forward-compatible. |
| Default branch saves immediately on `Select` change (no modal Save button needed) | Mirrors Kanban toolbar UX (`onBaseBranchChange` fires `project:set-default-branch` directly). Folding into modal save would duplicate validation and fight optimistic cache update. |
| Reuse existing `project:set-default-branch` IPC instead of inventing new save path | Already validates branch exists in `git:list-branches`. |
| `git-branches` query in modal uses `fetch:false` | Opening Settings shouldn't trigger a network `git fetch`. User can hit refresh icon explicitly — same pattern Kanban toolbar uses on initial render. |
| `RefreshCw` imported from `@shipshitdev/ui` (re-export), not direct `lucide-react` | App package has no direct lucide dep; matches existing `ThreadPanel.tsx` and `Titlebar.tsx`. |
| Icon button (no text label) for both refresh actions | Matches `BoardToolbar` icon button next to the Kanban dropdown. Tooltip carries the verb. |
| Fall back to plain text + load button when branches list empty | First open of Settings before any `git:list-branches` call → no dropdown to populate. Cheaper than auto-fetching on render. |

## Session 13 — Activity Heatmap (GitHub-style contribution grid)

### Context

PRD filed as GitHub issue #87 first, then implemented directly (skipping pipeline planner). Three rendering surfaces: global Costs dashboard, project-level Insights tab, per-issue CostsTab embedded mini-heatmap. Configurable range presets 30/90/365 days, four metrics (costUsd, prsOpened, tokens, runs).

### System Flow

```
Renderer <ActivityHeatmap scope|surface|projectId|threadId>
   │  React Query (queryKey = scope+ids+rangeDays+metric)
   ▼
IPC 'activity-heatmap:query'
   │
   ▼
HeatmapQueries.byScope(args)
   ├─► main metrics SQL  (pipeline_step_log + threads + projects)
   └─► PR dedupe SQL     (MIN(date(completed_at)) per thread_id WHERE shipping_completed AND github_pr_number IS NOT NULL)
   │
   ▼
HeatmapDayRecord[]  (zero-filled across rangeDays window)
   │
   ▼
quantile bucket → 5-step intensity (empty + q1..q4)
   │
   ▼
7×N week grid (Sunday-aligned, UTC)  +  native title tooltip  +  legend  +  metric/range tabs persisted to localStorage
```

### Key decisions

- **PR dedupe via separate SQL** (not JOIN/subquery in main metrics) — semantics: one PR per thread, dated by `MIN(date(completed_at))`. Simpler than window funcs in sqlite, easier to test.
- **Zero-fill in TypeScript, not SQL** — sqlite generate_series workarounds messy; do it after row fetch with a Map keyed by `YYYY-MM-DD`.
- **Quantile bucketing (q1–q4)** — matches GitHub's heatmap intensity feel; static thresholds would skew with cost outliers.
- **UTC anchoring** — avoid DST shifts breaking week alignment. Sunday-aligned grid.
- **localStorage keyed by `surface`** — global/project/issue persist independently. Issue surface fixes range=90, single metric (costUsd), no toggles.
- **`asRows<T>` cast helper** — already in `packages/db/src/utils.ts`; used for sqlite row safety.
