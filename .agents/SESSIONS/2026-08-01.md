# 2026-08-01

## Session 1 — execute-path git goes async

`execFileSync` on the per-node execute path froze the Electron main event loop for
the whole subprocess. `git add -A` on a large worktree is not fast, so the UI
stalled, IPC queued, and the pipeline heartbeat could not be written. The calls run
once per node *and* again per fan-out worker. `packages/git/src/checkpoint.ts`
already documented that git must be async — the execute path just never followed it.

### System flow — sync subprocess → locked async transport

```
before  (blocks the main loop for the whole git invocation)
  computeNodeDiff → execFileSync status → add -A → commit → diff
                    └── main process frozen ─────────────────┘

after
  computeNodeDiff → withGitLock(cwd, async run => {
                       status → add -A → commit → diff      ← one lock, one index
                    })
                    └── simple-git, event loop free ────────┘

withGitLock: promise queue keyed by path.resolve(cwd)
  /wt-a  ──[add]──[commit]──▶ ──[status]──▶     serialized: same index
  /wt-b  ──[add]──[commit]──▶                   parallel: distinct worktree
  chains off the previous holder's *settled* state, so one rejection
  neither poisons nor stalls the queue
```

### Key decisions
- **Per-cwd lock, not a global one.** `context.worktreePath ?? context.projectPath`
  means a worktree-less context falls back to the shared project repo, so a lock is
  mandatory — but keying it on the resolved path keeps fan-out workers fully
  parallel. Verified by a `peak === 2` concurrency test.
- **`withGitLock` is deliberately not reentrant.** Inside the callback you use the
  supplied `run`, never the exported `runGit`. `probeWorktreeChanges` therefore
  calls a lock-free `resolveDiffBaseWith(run, context)` body; the public
  `resolveWorktreeDiffBase` wraps that same body in its own lock. A test asserts the
  probe takes exactly one lock, guarding the self-deadlock.
- **One lock spans the whole probe.** Status and the base-vs-HEAD diff must observe
  the same index, not one straddling another caller's stage/commit.
- **Checkpoint keeps the unlocked variant.** Capture stages into an isolated
  `GIT_INDEX_FILE` and restore is off the per-node path, so neither contends for the
  real index. Importing `runGitUnlocked as runGit` left all ~20 callsites untouched.
- **Queue chains off *settled* state.** `previous.then(fn, fn)` — a rejected
  sequence must not poison or stall the next holder.
- **Used the existing async `resolveCurrentBranch`.** The related shared
  `getCurrentBranch` task has not landed, and none of the in-scope calls were
  `rev-parse --abbrev-ref HEAD`, so there is no collision either way.
- **Did not widen scope** to the remaining sync git in the verify/shipping path
  (`execution-phases.ts` ~1561-1598, all of `execution-shipping-phases.ts`). Same
  class of problem, once per turn rather than once per node — flagged as follow-up.

### Mistakes and fixes
- **17 `pipeline.test.ts` failures, all "Number of calls: 0".** Root cause:
  `pipeline.ts`'s `launch()` is fire-and-forget (`void (async () => …)()`), so
  `startX()` resolves after one microtask tick. Adding `await`s inside a phase
  pushed later side effects past the tests' single `await`. Fixed with the file's
  existing `flush()` helper at 26 sites. Diagnosed by committing WIP, reverting
  sources to master to prove the baseline green, then reading `launch()`.
- **Stub fidelity bug, caught before running.** My first mock did
  `String(await mockExecFileSync(...)).trim()`, which turns an unimplemented mock's
  `undefined` into the truthy string `'undefined'`. The sync original called
  `.trim()` on the result directly, so `undefined` *threw* and was caught. Both
  stubs now type the intermediate as `string`.
- **`mockWithGitLock` call counts leaked between tests** — a `vi.hoisted` mock is
  never auto-cleared. Added `mockWithGitLock.mockClear()`.
- **Bash cwd persists across calls** (again). A stray `cd packages/pipeline` broke
  later paths; use absolute paths.

### Gotchas discovered
- **`pipeline.test.ts` mocks `@shipcode/git` wholesale** (no `...actual`), unlike
  `execution-phases.test.ts` which spreads the real module. Any new git export the
  execute path uses must be added to that mock by hand or every affected test
  silently returns `undefined`.
- **`typecheck` has `dependsOn: ["^build"]`** — a bare
  `bun run --filter … typecheck` fails; it has to go through `bunx turbo`.
