# 2026-08-01

## Session 1 — stuck-thread watchdog was dead in production (`getStuck`)

`ThreadQueries.getStuck()` compared an ISO-stored `updated_at` against SQLite's
naive `datetime('now', ...)`. SQLite compares those columns as plain strings, so
the predicate was always false on the same calendar date — the watchdog matched
nothing and hung pipelines were never detected or recovered.

### System flow — why it never fired

```
write path (every thread mutation)
  ISO_NOW_SQL = strftime('%Y-%m-%dT%H:%M:%fZ','now')
    → updated_at = "2026-05-14T11:55:00.000Z"        ← 'T' at index 10 (0x54)

read path (watchdog, before)
  datetime('now','-120 seconds')
    → cutoff     = "2026-05-14 11:58:00"             ← ' ' at index 10 (0x20)

  updated_at <= cutoff
    → string compare: "2026-05-14" equal … then 'T' (0x54) > ' ' (0x20)
    → ALWAYS FALSE for any same-calendar-day pair
    → getStuck() returns []

caller: apps/desktop/src/main/index.ts  — setInterval 30s, HEARTBEAT_TIMEOUT_MS 120s
    → cutoff and updated_at are ALWAYS same-day → watchdog effectively disabled

read path (after)
  cutoff built in JS: new Date(Date.now() - thresholdMs).toISOString()
    → "2026-05-14T11:58:00.000Z"                     ← same canonical shape
    → bound as a parameter; comparison is now format-symmetric
```

### Affected components
- **Data** — `packages/db/src/queries/threads.ts` (`getStuck`)
- **Tests** — `packages/db/src/queries/threads.test.ts`
- **Shared** — `packages/shared/src/sqlite-time.ts` (docblock: comparison rule)
- **Consumer (unchanged)** — desktop main-process watchdog interval

### What was done
- [x] Built the threshold in JS and bound it as an ISO string; write format untouched.
- [x] Corrected the test that enshrined the bug — it seeded `updated_at` with
      `datetime('now', '-2 hours')`, so both sides matched wrongly and it passed
      against broken code. Now seeds the canonical ISO format production writes.
- [x] Added a same-calendar-day regression test with `vi.setSystemTime`, pinned to
      a fixed clock so it is deterministic regardless of when CI runs.
- [x] Confirmed both tests fail on the pre-fix query and pass after.
- [x] Swept for sibling bugs — no other production query compares a timestamp
      column against `datetime('now', ...)`.
- [x] `@shipcode/db` suite green (592 tests / 38 files), typecheck + Biome clean.

### Key decisions
- **Fixed the read side, not the write side.** `ISO_NOW_SQL` is the canonical write
  format, enforced by the `sqlite-time-usage.test.ts` guard. Changing writes would
  have broken that guard and every stored row.
- **Bound a JS-built cutoff rather than wrapping the column in `datetime()`.**
  Wrapping the column (`datetime(updated_at) <= datetime('now', ...)`) also works
  but defeats any index on `updated_at` and hides the format asymmetry instead of
  removing it.
- **Pinned the regression test's clock.** A "5 minutes ago" seed computed from the
  real clock straddles midnight in a narrow window; the whole point of the test is
  that both sides land on the same date, so the date must be fixed.
- **Left legacy naive rows alone.** All writes have used `ISO_NOW_SQL` for some
  time, so a row still in naive format cannot be recent — it sorts below any ISO
  cutoff and is correctly reported as stuck. No migration needed.
- **Recorded the comparison rule where it will be read** — `sqlite-time.ts`
  documented writes and reads but never comparisons, which is exactly the gap this
  bug fell through. Added there plus a hard-rule bullet in repo memory.

### Files changed

- `packages/db/src/queries/threads.test.ts` — ISO seeding helpers, corrected

### Mistakes and fixes
- **The guard test gave false assurance.** `sqlite-time-usage.test.ts` enforces the
  *write* format across query modules but says nothing about how those timestamps
  are compared, so a broken read predicate passed CI indefinitely. Worth considering
  a lint/guard for `datetime('now'` appearing in a comparison, not just a write.

### Next steps
- Consider extending `sqlite-time-usage.test.ts` to fail on any `datetime('now'`
  occurrence inside a `WHERE` clause in `queries/`.
- Watchdog behaviour is now reachable for the first time; watch for threads
  transitioning to `failed` that previously hung silently, in case
  `HEARTBEAT_TIMEOUT_MS = 120s` proves too aggressive for slow phases.
