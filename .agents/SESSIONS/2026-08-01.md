# 2026-08-01

## Session 1 — Unblock the main process: async PRD attachment staging + batched ref deletion

Two performance asks: synchronous `node:fs` in PRD attachment staging (runs in the
Electron main process, attachments up to 10 MB), and `for … await` deletion loops
that could be parallel. The second half turned out to be mostly a *don't* — see
Key decisions.

### System flow — where the blocking and the serialization were

```
prd-attachments:stage  (IPC, main process)
  for each file (≤ 6, cap enforced mid-loop)
    statSync        ─┐
    openSync/readSync│  all sync → event loop frozen for the whole staging pass
    closeSync        │
    copyFileSync    ─┘
  ⇣ now
    fs.stat / fs.open→handle.read→handle.close / fs.copyFile   (fs/promises)
    + post-await guard: session may have been cleared mid-flight
  ⇣ handler
    try/catch → log.error(full) → throw new Error(clampError(err))   (repo IPC rule)

pruneWorktreeArtifacts(worktreePath)          ← genuinely independent
  15 sibling top-level dirs, node_modules dominates
  for … await fs.rm  →  Promise.all(pruneArtifact)   + nesting guard
  per-item try/catch = allSettled semantics → { removed, missing, failed }

deleteThreadCheckpointRefs / deleteAllCheckpointRefs   ← NOT independent
  for … await git update-ref -d <ref>
    every deletion takes packed-refs.lock; N processes contend on 1 lock
  ⇣ instead of Promise.all
  git update-ref -z --stdin  ←  "delete <ref>\0\0" × N     (one process, one lock)
    transaction is all-or-nothing → on failure, fall back to the per-ref loop
```

### Key decisions
- **The ref-deletion loops are not a `Promise.all` candidate.** Git takes
  `packed-refs.lock` for *any* ref deletion, so concurrent `update-ref -d`
  processes contend on one lock with a short retry timeout and start failing —
  and the loops swallow failures, so the result would be a silent ref leak, not a
  visible error. Batching into one `update-ref -z --stdin` transaction is the real
  win: one process, one lock, one pass. Wire format verified in a throwaway repo
  before shipping.
- **`simple-git` has no stdin channel**, so `checkpoint.ts` spawns git directly in
  exactly one helper (`runGitWithStdin`) — the batch form has no argv equivalent.
- **Nesting guard on the artifact prune.** The default list is 15 siblings, but the
  function takes a caller-supplied list. If any target sits inside another,
  recursive removal of the parent races the child, so those fall back to ordered.
- **`stagePrdAttachments` stays serial.** Per-file decisions are not independent:
  each is deduped against everything already staged and counted against a cap that
  `break`s the loop. The cap is 6 files — there is nothing to win.
- **Worktree/branch removal in the pipeline stays serial**, same shared-repo-lock
  reason. Comments added so the next reader doesn't "fix" it.
- **Left one blocking read alone** — `fs.readFileSync(skillPath)` at
  `register-github-handlers.ts:1625`. Same class of problem, outside the stated
  scope, flagged rather than folded in.
