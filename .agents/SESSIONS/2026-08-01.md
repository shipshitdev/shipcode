# 2026-08-01

## Session 1 — CLI exit codes: failures no longer report success

HIGH bug: every guarded `shipcode` command printed a failure message and exited
`0`, so `shipcode run 123 && deploy` deployed on an unconfigured machine. Same
shape in the interactive terminal command, which wrote a `failed` thread status
to the DB and still exited `0`.

### System flow — where the exit code was lost

```
shipcode <cmd> <issue>
  └── requireOnboarding()                     apps/cli/src/commands/guard.ts
        ├── no ~/.shipcode/data/shipcode.db  → console.log + return false
        ├── onboardingVersion too old        → console.log + return false
        └── getDatabase() throws             → console.log + return false
                                                          │
       caller: `if (!requireOnboarding()) return;`  ───────┘
       action handler returns → commander resolves → node exits 0   ← the bug

shipcode terminal <issue>
  └── settle(exitCode)                        apps/cli/src/commands/terminal.ts
        exitCode !== 0 → threads.updateStatus(id, 'failed', …)  (DB only)
                       → node exits 0                            ← the bug

after:
  every failure branch → markCliFailure()      apps/cli/src/exit-code.ts
                       → process.exitCode = 1  (deferred; streams still flush)
```

### Affected components
- **CLI guard** — `guard.ts` (all three onboarding failure paths)
- **CLI commands** — `terminal.ts` `settle()`, `plan.ts`, `review.ts`, `start.ts`
- **CLI convention** — new `apps/cli/src/exit-code.ts`
- **Tests** — new subprocess suite + `process.exitCode` assertions in five unit suites

### Key decisions

- **`process.exitCode` over `process.exit()` for return-style failures.** These
  commands stream output; a hard exit can truncate it. `process.exitCode` lets the
  handler unwind and Node flush. Hard failures that must abort mid-function keep
  `process.exit(1)` — its `never` return type is what narrows the types after the
  guard, so replacing those would have been a regression, not a cleanup.

- **One code, `1`.** Checked for a convention before inventing one. There wasn't a
  richer scheme, and per-failure codes would be a new public contract for a
  pre-release CLI.

- **Subprocess tests, not return-value tests.** Every guarded command returns early
  from its action handler on failure, so a unit test asserting on the return value
  sees the same thing whether or not the exit code is set — which is exactly how
  this shipped. The suite builds `dist/` in `beforeAll` (tsup, ~0.3s), points
  `HOME` at a temp dir to simulate an un-onboarded machine, and asserts
  `status === 1`. Negative check: reverting `guard.ts` turns it red (7 failed / 2
  passed), so the test genuinely covers the reported bug.

- **Deliberately left exiting `0`** — empty state is a successful report, the way
  `git status` succeeds in a repo with no commits:
  - `status.ts` — "No ShipCode database found" (pinned by a test so the guard is
    not added by reflex)
  - `logs.ts` — "No terminal events recorded." (thread exists, result is empty)
  - `terminal.ts` `terminalSummaryCommand` — "No interactive terminal summary saved yet."
  - `prd.ts` — "No writing-prds skill found… Using default template." (recovers)

### Mistakes and fixes

- **`git stash` is shared across every worktree — do not use it here.** To prove the
  new subprocess test was a real regression test I stashed `guard.ts`, ran the suite
  (correctly red), and popped. The stash stack lives in the common git dir, and this
  repo has 26 active worktrees: a concurrent session popped the entry first. My
  `guard.ts` fix was lost and 12 unrelated files from that session's stash landed
  dirty in this worktree. Recovery: saved their diff to the session scratchpad,
  re-applied `guard.ts` by hand, and staged only the CLI paths (no `git add .`).
  For future negative checks use a scratch copy of the file, or `git show
  HEAD:path > path`, never `git stash`.
