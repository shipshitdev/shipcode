# 2026-08-01

## Session 1 — Code browser kept a stale file across automatic worktree switches

MEDIUM bug in `apps/desktop/src/renderer/features/project/code-browser.tsx`. The
component picks a fallback worktree on its own whenever the browsed worktree
disappears from a `git:visualizer-data` refetch (thread finished, worktree
removed). That automatic switch changed the active worktree but left
`selectedPath` untouched — the reset only existed in the manual `Select`
handler. The open path was then re-resolved against the *new* worktree: a
same-named file silently rendered different contents, and a missing one produced
a bare "not found" with no hint that the tree had changed underneath.

### System flow — before vs after

```
BEFORE — two independent reset sites, only one of them wired up
  manual picker  → setSelectedWorktreePath(next) + setSelectedPath(null)   ✅
  auto fallback  → setSelectedWorktreePath(next)                           ❌ stale path survives
                     └── code:read-file(newWorktree, oldPath) → wrong file / bogus error

AFTER — one selection value, one reconciliation effect
  selection = { worktreePath, relativePath }        ← the path carries its origin
  selectedPath = selection.worktreePath === active ? selection.relativePath : null
                     └── a carried-over path renders as "nothing selected" immediately

  useEffect([activeProjectId, selectedWorktreePath, selection])
    fires on ANY worktree change (auto fallback AND manual picker)
      → fetchQuery code:list-tree(newWorktree, parentDirOf(path))
          ├── entry exists as a file → re-tag selection to newWorktree  (selection survives)
          └── absent / dir missing   → setSelection(null)               (selection dropped)
```

### Affected components

- **Renderer** — `code-browser.tsx` only. No IPC, main-process, or schema change.

### What was done

- [x] Replaced `selectedPath: string | null` state with
      `selection: { worktreePath, relativePath } | null`.
- [x] Derived `selectedPath` from `selection`, gated on the worktree matching —
      a stale selection can never reach `FileViewer` even for one render.
- [x] Added the single reconciliation `useEffect` keyed on the active worktree,
      so the auto and manual paths cannot diverge again.
- [x] Removed the now-redundant reset from the manual picker handler.
- [x] Existence validation reuses `code:list-tree` on the file's parent
      directory via `queryClient.fetchQuery`, on the exact same
      `['code-tree', projectId, worktreePath, parentPath]` key the tree already
      uses — no new IPC surface, and the fetch warms the cache the tree renders
      from. Rejection (parent dir gone → handler throws `Not a directory`) is
      treated as "does not exist".
- [x] `cancelled` flag in the effect cleanup so a fast second switch cannot let
      a late resolution overwrite the newer selection.
- [x] Hoisted the duplicated `staleTime: 10_000` literals into
      `CODE_TREE_STALE_TIME` so the validation fetch and the tree queries stay
      in lockstep.
- [x] Two tests for the automatic switch (picker never touched — the worktree
      is removed from a `git:visualizer-data` refetch): path missing in the new
      worktree → selection dropped, no `code:read-file` against the new
      worktree; path present → selection kept and re-read from the new worktree.

### Key decisions

- **Keep the selection when the path exists, don't blanket-clear.** Switching
  between a thread worktree and `main` on the same file is the common case;
  clearing every time is worse UX. But keeping is only safe *after* verifying
  the file is really there, which is why the effect validates instead of
  assuming.
- **Tag the selection with its worktree rather than adding a second "reset"
  call.** A copy-pasted reset in the auto path would have fixed today's bug and
  left the same divergence available to the next code path that changes
  worktrees. Making the origin part of the value means an unreconciled
  selection is structurally unrenderable.
- **Validate through the existing tree channel.** `code:list-tree` on the parent
  dir already returns `type` per entry, so no `code:exists` handler was needed.

### Mistakes and fixes

- **`git stash` ate the work — do not use it in this repo.** `refs/stash` is a
  single ref shared by every worktree of a repository, and this checkout has ~26
  live worktrees. A concurrent session's stash push/pop interleaved with mine:
  my two files reverted to HEAD, four unrelated `packages/git` /
  `packages/shared` files appeared modified, and `git stash list` came back
  empty. Every edit had to be re-applied from context. To prove a test is
  non-vacuous here, copy the file aside or use `git diff > patch` — never stash.
- Foreign uncommitted changes from that other session
  (`packages/git/src/worktree-safety*.ts`,
  `packages/shared/src/worktree-path*.ts`) are still sitting in this worktree.
  Left untouched; staged by explicit path so they are not swept into this
  commit.
- `apps/desktop/src/main/git-workflows.test.ts:558` fails locally with a
  `/var` vs `/private/var` worktree path mismatch. Confirmed pre-existing and
  environmental — it fails identically with these changes reverted.
