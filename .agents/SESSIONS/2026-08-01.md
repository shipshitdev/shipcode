# 2026-08-01

## Session 1 — Memoize list-view rows so the 5s issue poll stops re-rendering the board

List view (`IssueListView`) re-rendered every row on every 5-second issue poll.
Its direct counterpart in card view (`DraggableCard`) has been memoized all along —
the list row was a single missed instance of the same pattern.

### System flow — why the poll reached the rows

```
IssuesPanel
  useQuery(['github-issues', projectId], staleTime: 5_000)
    → poll settles every 5s → IssuesPanel re-renders
       │  React Query structural sharing keeps unchanged issue objects identical,
       │  so `issues` entries are referentially stable across polls…
       ↓
    KanbanBoard
      badge/staleness Maps already useMemo'd on boardIssues
      onIssueClick / onOpenPullRequest / onArchiveIssue passed straight through
       ↓
    IssueListView → getListRowProps(issue, …) → DraggableListRow
       ✗ not memoized      → every row re-renders unconditionally
       ✗ callbacks unstable → memo alone would have been decorative
```

Both halves had to change: the memo, and the parent handlers feeding it.

### Affected components
- **UI package** — `packages/ui/src/kanban-board/IssueListView.tsx`
- **Desktop renderer** — `apps/desktop/src/renderer/components/IssuesPanel.tsx`

### What was done
- [x] Wrapped `DraggableListRow` in `memo()` following `DraggableCard` exactly —
      plain `memo`, default shallow compare, `Component` suffix on the inner
      function, explicit `displayName`.
- [x] Audited every sibling in `packages/ui/src/kanban-board/`: `DraggableCard` was
      the only memoized component; the rest (`DroppableColumn`, `StackedColumn`,
      `SectionBlock`, `ListSectionBlock`, `ColumnHeader`, `BoardToolbar`,
      `HiddenColumnsPanel`) are containers taking rebuilt Maps, not per-issue leaves.
      The list row was the single instance of the asymmetry.
- [x] Stabilized the three handlers that reach the row in `IssuesPanel`:
      `handleIssueClick` and `handleIssueComment` wrapped in `useCallback`; the
      inline `onOpenPullRequest` and `onArchiveIssue` arrows hoisted into
      `useCallback` handlers.
- [x] Added `IssueListView.memo.test.tsx` — a render-count instrument, not a
      smoke test. `formatDate` is called exactly once per row render and nowhere
      else in the file, so a spy on it counts row renders precisely.
- [x] ui 245/245, ui + desktop typecheck clean, desktop 1596/1597 (the one failure
      is the documented macOS `/var` symlink issue from #488).

### What was measured

`formatDate` spy call counts across a parent re-render, 3 rows:

| scenario | before | after |
|---|---|---|
| poll settles with identical data | 3 / 3 rows | **0 / 3** |
| one issue's title changes | 3 / 3 rows | **1 / 3** |
| a callback prop gets a fresh identity | 3 / 3 | 3 / 3 (guard test) |

The third row of the table is deliberate: it fails if anyone reintroduces an
inline arrow in the parent, which is the failure mode that would silently make
the memo decorative again.

### Key decisions
- **Plain `memo`, no custom comparator.** `DraggableCard` uses default shallow
  compare; the instruction was to match it exactly. A custom comparator would also
  have to be maintained against 14 props.
- **Stabilized only the handlers that reach the memoized row.** `onOpenExternal` is
  an identical inline arrow but only reaches `BoardToolbar` / `ProjectLinks`, which
  are not memoized — wrapping it would buy nothing and widen the diff.
- **Left badge-object churn alone.** The badge Maps are memoized on `boardIssues`,
  so when *any* issue changes, every non-null badge object is rebuilt and rows
  carrying badges still re-render. Rows with all-null badges (the common case)
  are unaffected. Fixing it needs per-issue badge identity caching (WeakMap or
  similar) — machinery that exists nowhere else in this codebase. Noted as
  follow-up rather than invented here.

### Mistakes and fixes
- **`git stash` in this repo is dangerous — the stash stack is repo-global and
  shared by all 27 worktrees.** Stashed to check whether a desktop test failure was
  pre-existing; another session (`claude/relaxed-matsumoto-0de531`) raced the same
  stack, and `git stash pop` restored *their* `safesend-wip` into this worktree
  while this session's work went to theirs. Recovered both from dangling stash
  commits (`git fsck --no-reflogs`, matched by branch name in the stash message).
  **Never `git stash` here — use a patch file or a throwaway commit.**
- **Vitest could not resolve `@dnd-kit/core`, then `@shipcode/shared`.** The
  worktree had no installed deps and no build output. `bun install`, then
  `bunx turbo run build --filter=@shipcode/shared`. Same failure mode as 07-31.
- **Biome reordered an unrelated import** (`ColumnHeader` above `./constants`) while
  formatting. Reverting it to keep the diff scoped was pointless — the pre-commit
  hook runs Biome on staged files and puts it straight back. It is pre-existing
  drift in the file that the hook fixes on first touch; let it through.
