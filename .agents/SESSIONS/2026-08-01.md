### The N+1 — `markNodeCompletedAndPromote`

Every node completion did `1 + N` queries: one to list the completed node's
dependents, then one blocker-count query **per dependent**. Graph width is the
multiplier, and this sits on the hot pipeline path (fires on each node
completion).

```
before:  SELECT dependents            (1)
         for each dependent:
           SELECT COUNT(incomplete blockers)   (N)
           if 0 → UPDATE … status='ready'

after:   SELECT dependents
           LEFT JOIN blocker edges
           LEFT JOIN blocker nodes ON … AND status != 'completed'
          GROUP BY dependent
         HAVING COUNT(blocker_source.id) = 0    (1, total)
          ORDER BY MIN(dependent.rowid)
         for each promotable → UPDATE (prepared once)
```

Equivalence argument: the promote loop only writes `'ready'`, never
`'completed'`, so no blocker's `status != 'completed'` predicate can flip
mid-loop. Blocker counts are stable for the whole pass ⇒ one grouped snapshot ==
re-counting per dependent. The `status != 'completed'` predicate lives in the
join's `ON` clause, so completed sources yield NULL and drop out of
`COUNT(blocker_source.id)`.

Preserved deliberately:
- **Transaction** — query, promote loop, completion write and the
  graph-completion check all still sit inside the one `transaction(this.db, …)`.
- **Ordering** — `ORDER BY MIN(dependent.rowid)` reproduces the edge-insertion
  order the old unordered scan iterated in.
- **`ISO_NOW_SQL`** — untouched on every write (guard test
  `sqlite-time-usage.test.ts`).
