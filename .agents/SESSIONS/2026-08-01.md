# 2026-08-01

## Session 1 — DRY: fold the quick-task launch path into `launchIssuePipeline`

Audit follow-up. `PipelineScheduler._launchQuickTask` hand-rebuilt the shared
launcher's 13-field phase-model options bag plus its failure/clamping flow, so any
future change to model routing, phase defaults, or failure handling would land on
`launchIssuePipeline` and silently miss quick tasks.

### System flow — one launcher, two modes

```
PipelineScheduler
  startOrQueue          → _launch          ─┐
  startQuickTaskOrQueue → _launchQuickTask ─┤
  onSlotFreed (drain)   → either            │
                                            ▼
                              _dispatchLaunch(issue, project, mode)
                                 resolveIssuePhaseModels(settings, project, issue)
                                            ▼
                              launchIssuePipeline(deps, {…, mode}, hooks)
                                 shared: active-thread guard, pipeline status,
                                         updateIssueContent, linkThread,
                                         try { validatePhaseModels
                                               setPhaseModels
                                               resetFailureTracking
                                               supersedeAll(+ForIssue)
                                               dispatch }
                                         catch → onLaunchError → transitionThreadPhase(failed)
                                            │
                        mode = github-issue ─┤─ mode = quick-task
                          setGithubIssue     │   setGithubIssueNumber   (github_repo stays null)
                          reuse-or-create    │   require pre-linked thread
                          startFromGitHubIssue   startFromQuickTask
```

### Key decisions
- **Mode parameter, not a second launcher or a wrapper.** The three real
  differences (thread acquisition, GitHub stamping, dispatch fn) are three short
  branches; a wrapper would have had to re-own the try/catch, which is exactly the
  thing that drifted.
- **Quick tasks require a pre-linked thread.** `pipeline:create-quick-task` inserts
  the cache row with its thread already linked, so a missing thread means a corrupt
  row — creating one would start a run against a synthetic negative sentinel issue
  number. Kept as an explicit throw rather than falling through to reuse-or-create.
- **`setGithubIssueNumber`, never `setGithubIssue`, in quick mode.** `github_repo`
  must stay null or the pipeline's `isRealGithubIssueNumber` guards start seeing a
  repo they cannot address.
- **Drift is reported, not preserved.** Three latent bugs (below) are fixed by the
  delegation and called out in the PR body instead of being replicated.

### Drift the fork was hiding (now fixed)
1. **No active-thread guard.** Quick tasks never checked
   `REUSABLE_THREAD_STATUSES` (failed/completed/idle), so a relaunch could land on
   a thread mid-run. Safe for the queue-drain path — `threads.status` defaults to
   `'idle'`.
2. **`validatePhaseModels` ran outside the try.** An unsupported model or missing
   API key rejected *after* the issue was moved to `planning`, with no
   `transitionThreadPhase(failed)` — the thread was stranded in `planning` forever.
   This is precisely the bug the shared launcher's comment says it fixed; quick
   tasks still had it.
3. **`setPhaseModels` / `resetFailureTracking` / `supersedeAll` outside the try** —
   same class, same consequence.
4. **Redundant `resolveExecutorModelForIssue`.** Provably identical to
   `resolveIssuePhaseModels(...).executorModel` (both delegate to
   `resolvePhaseModelForIssue(..., 'executor')`), so the
   `{...phaseModels, executorModel}` spread was a no-op.

### Newly uniform, verified no-ops
- `updateIssueContent` now fires for quick tasks — `threads.create(projectId, trimmed, title)`
  and `insertQuickTask({title, body: trimmed})` are written from the same text.
- `githubIssues.linkThread` — the row already points at the same thread id; idempotent.
- `plans.supersedeAllForIssue` — sentinel issue numbers are unique per row and
  `excludeThreadId` is this thread, so nothing is superseded.
- `executorModelOverride: null` explicit instead of omitted — `bootstrapPipelineRun`
  already normalizes with `?? null`.
