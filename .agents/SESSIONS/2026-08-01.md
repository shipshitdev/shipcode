## Session 1 — stuck-thread watchdog was dead in production (`getStuck`)

`ThreadQueries.getStuck()` compared an ISO-stored `updated_at` against SQLite's
naive `datetime('now', ...)`. SQLite compares those columns as plain strings, so
the predicate was always false on the same calendar date — the watchdog matched
nothing and hung pipelines were never detected or recovered.

### System flow — why it never fired

```
write path (every thread mutation)
  ISO_NOW_SQL = strftime('%Y-%m-%dT%H:%M:%fZ','now')
    → updated_at = "2026-05-14T11:55:00.000Z"        ← 'T' at index 10 (0x54)

read path (watchdog, before)
  datetime('now','-120 seconds')
    → cutoff     = "2026-05-14 11:58:00"             ← ' ' at index 10 (0x20)

  updated_at <= cutoff
    → string compare: "2026-05-14" equal … then 'T' (0x54) > ' ' (0x20)
    → ALWAYS FALSE for any same-calendar-day pair
    → getStuck() returns []

caller: apps/desktop/src/main/index.ts  — setInterval 30s, HEARTBEAT_TIMEOUT_MS 120s
    → cutoff and updated_at are ALWAYS same-day → watchdog effectively disabled

read path (after)
  cutoff built in JS: new Date(Date.now() - thresholdMs).toISOString()
    → "2026-05-14T11:58:00.000Z"                     ← same canonical shape
    → bound as a parameter; comparison is now format-symmetric
```

### Affected components
- **Data** — `packages/db/src/queries/threads.ts` (`getStuck`)
- **Tests** — `packages/db/src/queries/threads.test.ts`
- **Shared** — `packages/shared/src/sqlite-time.ts` (docblock: comparison rule)
- **Consumer (unchanged)** — desktop main-process watchdog interval

### What was done
- [x] Built the threshold in JS and bound it as an ISO string; write format untouched.
- [x] Corrected the test that enshrined the bug — it seeded `updated_at` with
      `datetime('now', '-2 hours')`, so both sides matched wrongly and it passed
      against broken code. Now seeds the canonical ISO format production writes.
- [x] Added a same-calendar-day regression test with `vi.setSystemTime`, pinned to
      a fixed clock so it is deterministic regardless of when CI runs.
- [x] Confirmed both tests fail on the pre-fix query and pass after.
- [x] Swept for sibling bugs — no other production query compares a timestamp
      column against `datetime('now', ...)`.
- [x] `@shipcode/db` suite green (592 tests / 38 files), typecheck + Biome clean.

### Key decisions
- **Fixed the read side, not the write side.** `ISO_NOW_SQL` is the canonical write
  format, enforced by the `sqlite-time-usage.test.ts` guard. Changing writes would
  have broken that guard and every stored row.
- **Bound a JS-built cutoff rather than wrapping the column in `datetime()`.**
  Wrapping the column (`datetime(updated_at) <= datetime('now', ...)`) also works
  but defeats any index on `updated_at` and hides the format asymmetry instead of
  removing it.
- **Pinned the regression test's clock.** A "5 minutes ago" seed computed from the
  real clock straddles midnight in a narrow window; the whole point of the test is
  that both sides land on the same date, so the date must be fixed.
- **Left legacy naive rows alone.** All writes have used `ISO_NOW_SQL` for some
  time, so a row still in naive format cannot be recent — it sorts below any ISO
  cutoff and is correctly reported as stuck. No migration needed.
- **Recorded the comparison rule where it will be read** — `sqlite-time.ts`
  documented writes and reads but never comparisons, which is exactly the gap this
  bug fell through. Added there plus a hard-rule bullet in repo memory.

### Files changed
- `packages/db/src/queries/threads.ts` — JS-built ISO cutoff + explanatory docblock
- `packages/db/src/queries/threads.test.ts` — ISO seeding helpers, corrected
  existing assertion, new same-day regression case
- `packages/shared/src/sqlite-time.ts` — comparison guidance in the module docblock
- `.agents/memory/MEMORY.md` — new hard rule

### Mistakes and fixes
- **The guard test gave false assurance.** `sqlite-time-usage.test.ts` enforces the
  *write* format across query modules but says nothing about how those timestamps
  are compared, so a broken read predicate passed CI indefinitely. Worth considering
  a lint/guard for `datetime('now'` appearing in a comparison, not just a write.

### Next steps
- Consider extending `sqlite-time-usage.test.ts` to fail on any `datetime('now'`

## Session 2 — DRY: fold the quick-task launch path into `launchIssuePipeline`

Audit follow-up. `PipelineScheduler._launchQuickTask` hand-rebuilt the shared
launcher's 13-field phase-model options bag plus its failure/clamping flow, so any
future change to model routing, phase defaults, or failure handling would land on
`launchIssuePipeline` and silently miss quick tasks.

### System flow — one launcher, two modes

```
PipelineScheduler
  startOrQueue          → _launch          ─┐
  startQuickTaskOrQueue → _launchQuickTask ─┤
  onSlotFreed (drain)   → either            │
                                            ▼
                              _dispatchLaunch(issue, project, mode)
                                 resolveIssuePhaseModels(settings, project, issue)
                                            ▼
                              launchIssuePipeline(deps, {…, mode}, hooks)
                                 shared: active-thread guard, pipeline status,
                                         updateIssueContent, linkThread,
                                         try { validatePhaseModels
                                               setPhaseModels
                                               resetFailureTracking
                                               supersedeAll(+ForIssue)
                                               dispatch }
                                         catch → onLaunchError → transitionThreadPhase(failed)
                                            │
                        mode = github-issue ─┤─ mode = quick-task
                          setGithubIssue     │   setGithubIssueNumber   (github_repo stays null)
                          reuse-or-create    │   require pre-linked thread
                          startFromGitHubIssue   startFromQuickTask
```

### Affected components
- **Pipeline** — `packages/pipeline/src/issue-launch.ts` (mode-aware launcher), `index.ts` (barrel)
- **Main process** — `apps/desktop/src/main/pipeline-scheduler.ts` (`_dispatchLaunch`)
- **Tests** — `issue-launch.test.ts` (+6 quick-task cases), `pipeline-scheduler.test.ts` (+3)

### What was done
- [x] Diffed `_launchQuickTask` against `launchIssuePipeline` line by line before
      writing any code; classified every delta as genuine difference vs. drift.
- [x] Added `ISSUE_LAUNCH_MODE` / `IssueLaunchMode` and a `mode` input to the
      launcher; the three genuine differences became branches inside it.
- [x] `_launch` and `_launchQuickTask` are now two-line wrappers over a shared
      private `_dispatchLaunch(issue, project, mode)` — identical hooks for both.
- [x] Dropped the now-unused `resolveExecutorModelForIssue` import from the scheduler.
- [x] Tests: 12 pass in `issue-launch.test.ts`, 57 in `pipeline-scheduler.test.ts`.
- [x] Typecheck 15/15, biome clean on all 5 changed files.

### Key decisions
- **Mode parameter, not a second launcher or a wrapper.** The three real
  differences (thread acquisition, GitHub stamping, dispatch fn) are three short
  branches; a wrapper would have had to re-own the try/catch, which is exactly the
  thing that drifted.
- **Quick tasks require a pre-linked thread.** `pipeline:create-quick-task` inserts
  the cache row with its thread already linked, so a missing thread means a corrupt
  row — creating one would start a run against a synthetic negative sentinel issue
  number. Kept as an explicit throw rather than falling through to reuse-or-create.
- **`setGithubIssueNumber`, never `setGithubIssue`, in quick mode.** `github_repo`
  must stay null or the pipeline's `isRealGithubIssueNumber` guards start seeing a
  repo they cannot address.
- **Drift is reported, not preserved.** Three latent bugs (below) are fixed by the
  delegation and called out in the PR body instead of being replicated.

### Drift the fork was hiding (now fixed)
1. **No active-thread guard.** Quick tasks never checked
   `REUSABLE_THREAD_STATUSES` (failed/completed/idle), so a relaunch could land on
   a thread mid-run. Safe for the queue-drain path — `threads.status` defaults to
   `'idle'`.
2. **`validatePhaseModels` ran outside the try.** An unsupported model or missing
   API key rejected *after* the issue was moved to `planning`, with no
   `transitionThreadPhase(failed)` — the thread was stranded in `planning` forever.
   This is precisely the bug the shared launcher's comment says it fixed; quick
   tasks still had it.
3. **`setPhaseModels` / `resetFailureTracking` / `supersedeAll` outside the try** —
   same class, same consequence.
4. **Redundant `resolveExecutorModelForIssue`.** Provably identical to
   `resolveIssuePhaseModels(...).executorModel` (both delegate to
   `resolvePhaseModelForIssue(..., 'executor')`), so the
   `{...phaseModels, executorModel}` spread was a no-op.

### Newly uniform, verified no-ops
- `updateIssueContent` now fires for quick tasks — `threads.create(projectId, trimmed, title)`
  and `insertQuickTask({title, body: trimmed})` are written from the same text.
- `githubIssues.linkThread` — the row already points at the same thread id; idempotent.
- `plans.supersedeAllForIssue` — sentinel issue numbers are unique per row and
  `excludeThreadId` is this thread, so nothing is superseded.
- `executorModelOverride: null` explicit instead of omitted — `bootstrapPipelineRun`
  already normalizes with `?? null`.

`apps/desktop/src/main/pipeline-scheduler.{ts,test.ts}`.

## Session 3 — Code browser kept a stale file across automatic worktree switches

MEDIUM bug in `apps/desktop/src/renderer/features/project/code-browser.tsx`. The
component picks a fallback worktree on its own whenever the browsed worktree
disappears from a `git:visualizer-data` refetch (thread finished, worktree
removed). That automatic switch changed the active worktree but left
`selectedPath` untouched — the reset only existed in the manual `Select`
handler. The open path was then re-resolved against the *new* worktree: a
same-named file silently rendered different contents, and a missing one produced
a bare "not found" with no hint that the tree had changed underneath.

### System flow — before vs after

```
BEFORE — two independent reset sites, only one of them wired up
  manual picker  → setSelectedWorktreePath(next) + setSelectedPath(null)   ✅
  auto fallback  → setSelectedWorktreePath(next)                           ❌ stale path survives
                     └── code:read-file(newWorktree, oldPath) → wrong file / bogus error

AFTER — one selection value, one reconciliation effect
  selection = { worktreePath, relativePath }        ← the path carries its origin
  selectedPath = selection.worktreePath === active ? selection.relativePath : null
                     └── a carried-over path renders as "nothing selected" immediately

  useEffect([activeProjectId, selectedWorktreePath, selection])
    fires on ANY worktree change (auto fallback AND manual picker)
      → fetchQuery code:list-tree(newWorktree, parentDirOf(path))
          ├── entry exists as a file → re-tag selection to newWorktree  (selection survives)
          └── absent / dir missing   → setSelection(null)               (selection dropped)
```

### Affected components

- **Renderer** — `code-browser.tsx` only. No IPC, main-process, or schema change.

### What was done

- [x] Replaced `selectedPath: string | null` state with
      `selection: { worktreePath, relativePath } | null`.
- [x] Derived `selectedPath` from `selection`, gated on the worktree matching —
      a stale selection can never reach `FileViewer` even for one render.
- [x] Added the single reconciliation `useEffect` keyed on the active worktree,
      so the auto and manual paths cannot diverge again.
- [x] Removed the now-redundant reset from the manual picker handler.
- [x] Existence validation reuses `code:list-tree` on the file's parent
      directory via `queryClient.fetchQuery`, on the exact same
      `['code-tree', projectId, worktreePath, parentPath]` key the tree already
      uses — no new IPC surface, and the fetch warms the cache the tree renders
      from. Rejection (parent dir gone → handler throws `Not a directory`) is
      treated as "does not exist".
- [x] `cancelled` flag in the effect cleanup so a fast second switch cannot let
      a late resolution overwrite the newer selection.
- [x] Hoisted the duplicated `staleTime: 10_000` literals into
      `CODE_TREE_STALE_TIME` so the validation fetch and the tree queries stay
      in lockstep.
- [x] Two tests for the automatic switch (picker never touched — the worktree
      is removed from a `git:visualizer-data` refetch): path missing in the new
      worktree → selection dropped, no `code:read-file` against the new
      worktree; path present → selection kept and re-read from the new worktree.

### Key decisions

- **Keep the selection when the path exists, don't blanket-clear.** Switching
  between a thread worktree and `main` on the same file is the common case;
  clearing every time is worse UX. But keeping is only safe *after* verifying
  the file is really there, which is why the effect validates instead of
  assuming.
- **Tag the selection with its worktree rather than adding a second "reset"
  call.** A copy-pasted reset in the auto path would have fixed today's bug and
  left the same divergence available to the next code path that changes
  worktrees. Making the origin part of the value means an unreconciled
  selection is structurally unrenderable.
- **Validate through the existing tree channel.** `code:list-tree` on the parent
  dir already returns `type` per entry, so no `code:exists` handler was needed.

## Session 4 — db query hot-path: N+1 promote + statements re-prepared in loops

Worktree `loving-ptolemy-7b53eb`, branch `claude/loving-ptolemy-7b53eb`.
Scope: `packages/db/src/queries/` only. No schema change, no behaviour change.

### The N+1 — `markNodeCompletedAndPromote`

Every node completion did `1 + N` queries: one to list the completed node's
dependents, then one blocker-count query **per dependent**. Graph width is the
multiplier, and this sits on the hot pipeline path (fires on each node
completion).

```
before:  SELECT dependents            (1)
         for each dependent:
           SELECT COUNT(incomplete blockers)   (N)
           if 0 → UPDATE … status='ready'

after:   SELECT dependents
           LEFT JOIN blocker edges
           LEFT JOIN blocker nodes ON … AND status != 'completed'
          GROUP BY dependent
         HAVING COUNT(blocker_source.id) = 0    (1, total)
          ORDER BY MIN(dependent.rowid)
         for each promotable → UPDATE (prepared once)
```

Equivalence argument: the promote loop only writes `'ready'`, never
`'completed'`, so no blocker's `status != 'completed'` predicate can flip
mid-loop. Blocker counts are stable for the whole pass ⇒ one grouped snapshot ==
re-counting per dependent. The `status != 'completed'` predicate lives in the
join's `ON` clause, so completed sources yield NULL and drop out of
`COUNT(blocker_source.id)`.

Preserved deliberately:
- **Transaction** — query, promote loop, completion write and the
  graph-completion check all still sit inside the one `transaction(this.db, …)`.
- **Ordering** — `ORDER BY MIN(dependent.rowid)` reproduces the edge-insertion
  order the old unordered scan iterated in.
- **`ISO_NOW_SQL`** — untouched on every write (guard test
  `sqlite-time-usage.test.ts`).

### Statements hoisted out of loop bodies

`node:sqlite` `StatementSync` is reusable; re-`prepare()` per iteration throws
that away.

- `task-graphs.ts` — node INSERT and edge INSERT in `replaceForPlan`; the new
  promote UPDATE.
- `diffs.ts` — `replaceForThread` no longer calls `create()` per row (which
  re-prepared each time). Shared `INSERT_DIFF_SQL` + `diffInsertValues()` so
  both paths bind identically. `created_at` stays JS-side `toISOString()` —
  that table never used `ISO_NOW_SQL`.
- `issue-edges.ts` — `replaceBodyEdges` INSERT OR IGNORE.
- `triage-rules.ts` — `prepareInsert()` helper shared by `create()` and
  `replaceForProject`; `compactOrder` reorder UPDATE.

### Swept and left alone
- `automations.ts`, `checkpoints.ts`, `settings.ts`, `plans.ts` (chunked IN),
  `reviews.ts`, `dashboard.ts`, `heatmap.ts` — already batched or already
  hoisted.
- `review-findings.ts` `input.findings.map(createOrUpdateOpen)` — irreducible
  per-row upsert, not collapsible into one statement.
- `pipeline-analytics.getSlowestRecentRuns` — query-in-map but hard-bounded to
  5 rows; constant, does not scale.

### Verification
- `packages/db` — 38 files / 593 tests pass; `tsc --noEmit` clean.
- New tests in `task-graphs.test.ts`: a 9-node fan-out (`step-1 → step-2..8`,
  with `step-9` a second blocker on `step-5`/`step-6`) asserting the exact

## Session 5 — CLI exit codes: failures no longer report success

HIGH bug: every guarded `shipcode` command printed a failure message and exited
`0`, so `shipcode run 123 && deploy` deployed on an unconfigured machine. Same
shape in the interactive terminal command, which wrote a `failed` thread status
to the DB and still exited `0`.

### System flow — where the exit code was lost

```
shipcode <cmd> <issue>
  └── requireOnboarding()                     apps/cli/src/commands/guard.ts
        ├── no ~/.shipcode/data/shipcode.db  → console.log + return false
        ├── onboardingVersion too old        → console.log + return false
        └── getDatabase() throws             → console.log + return false
                                                          │
       caller: `if (!requireOnboarding()) return;`  ───────┘
       action handler returns → commander resolves → node exits 0   ← the bug

shipcode terminal <issue>
  └── settle(exitCode)                        apps/cli/src/commands/terminal.ts
        exitCode !== 0 → threads.updateStatus(id, 'failed', …)  (DB only)
                       → node exits 0                            ← the bug

after:
  every failure branch → markCliFailure()      apps/cli/src/exit-code.ts
                       → process.exitCode = 1  (deferred; streams still flush)
```

### Affected components
- **CLI guard** — `guard.ts` (all three onboarding failure paths)
- **CLI commands** — `terminal.ts` `settle()`, `plan.ts`, `review.ts`, `start.ts`
- **CLI convention** — new `apps/cli/src/exit-code.ts`
- **Tests** — new subprocess suite + `process.exitCode` assertions in five unit suites

### What was done
- [x] Swept all of `apps/cli/src/commands/` for the print-and-return shape rather
      than fixing only the two reported sites.
- [x] Checked for an existing code convention first: the CLI already uses a plain
      `process.exit(1)` in ~14 places and has no richer scheme, so `1` uniformly.
- [x] `exit-code.ts` — `CLI_FAILURE_EXIT_CODE` + `markCliFailure()` as the single
      grep-stable anchor.
- [x] `guard.ts` — all three paths mark failure; callers keep `if (!requireOnboarding()) return;`.
- [x] `terminal.ts` — `settle()` marks failure whenever the child exit code is non-zero.
- [x] `plan.ts` / `review.ts` — no-plan / no-review branches, plus a terminal
      `thread.status === PIPELINE_PHASE.failed` check.
- [x] `start.ts` — empty issue-number prompt.
- [x] Confirmed nothing depends on the always-`0` behaviour: nothing in `apps/` or
      `packages/` imports `apps/cli/src`, and `apps/desktop` depends only on
      `@shipcode/{agents,db,git,pipeline,shared,ui}`.
- [x] Subprocess tests in `apps/cli/src/cli-exit-code.test.ts` that run the built
      `dist/index.js` and assert the process status.
- [x] `bunx vitest run` in `apps/cli` → 20 files / 116 tests passed; `tsc --noEmit`
      clean; biome clean.

### Key decisions

- **`process.exitCode` over `process.exit()` for return-style failures.** These
  commands stream output; a hard exit can truncate it. `process.exitCode` lets the
  handler unwind and Node flush. Hard failures that must abort mid-function keep
  `process.exit(1)` — its `never` return type is what narrows the types after the
  guard, so replacing those would have been a regression, not a cleanup.

- **One code, `1`.** Checked for a convention before inventing one. There wasn't a
  richer scheme, and per-failure codes would be a new public contract for a
  pre-release CLI.

- **Subprocess tests, not return-value tests.** Every guarded command returns early
  from its action handler on failure, so a unit test asserting on the return value
  sees the same thing whether or not the exit code is set — which is exactly how
  this shipped. The suite builds `dist/` in `beforeAll` (tsup, ~0.3s), points
  `HOME` at a temp dir to simulate an un-onboarded machine, and asserts
  `status === 1`. Negative check: reverting `guard.ts` turns it red (7 failed / 2
  passed), so the test genuinely covers the reported bug.

- **Deliberately left exiting `0`** — empty state is a successful report, the way
  `git status` succeeds in a repo with no commits:
  - `status.ts` — "No ShipCode database found" (pinned by a test so the guard is
    not added by reflex)
  - `logs.ts` — "No terminal events recorded." (thread exists, result is empty)
  - `terminal.ts` `terminalSummaryCommand` — "No interactive terminal summary saved yet."
  - `prd.ts` — "No writing-prds skill found… Using default template." (recovers)

### Files changed
- `apps/cli/src/exit-code.ts` *(new)*
- `apps/cli/src/cli-exit-code.test.ts` *(new)*
- `apps/cli/src/commands/{guard,terminal,plan,review,start}.ts`
- `apps/cli/src/commands/{guard,terminal,plan,review,start}.test.ts`

### Mistakes and fixes

- **`git stash` is shared across every worktree — do not use it here.** To prove the

## Session 6 — Single source of truth for GitHub issue records

Bug report: issue status was hand-synced into two independent stores from two IPC
handlers in `apps/desktop/src/renderer/hooks/useIpc.ts`. Investigation found the
problem was wider than reported — **seven** parallel writers, not two.

### System flow — before and after

```
BEFORE — 7 writers, 2 stores, no owner
  useIpc: pipeline:phase          ──┬─> queryClient.setQueryData(['github-issues', p])
                                    └─> useAppStore.setState({ githubIssues, activeIssue })
  useIpc: github:issues-updated   ──┬─> setQueryData
                                    └─> setState({ githubIssues, activeIssue, activeThreadId })
  IssuesPanel.patchIssueOptimistic──┬─> setQueryData
                                    └─> setGithubIssues
  IssuesPanel useEffect mirror     ───> setGithubIssues   (only while panel mounted)
  CreateIssueModal                 ──┬─> setQueryData
                                    └─> setState
  OverviewView / CostsView /       ───> setGithubIssues   (cache bypassed entirely)
    InboxView  (cross-project nav)
        → board and detail view can disagree about the same issue

AFTER — 1 owner, 1 writer
  every producer ───> queryClient.setQueryData(['github-issues', projectId], …)
                                  │
                    queryCache.subscribe  (issue-cache-projection.ts)
                                  │
                                  ▼
                  useAppStore { githubIssues, activeIssue, activeThreadId }
                        read-only projection · no setter exists
```

### Affected components
- **Renderer stores** — new `issue-cache-projection.ts`; `app-store.ts` loses
  `setGithubIssues`

  `CostsView`, `InboxView`

### What was done
- [x] Read every consumer's subscription shape before choosing an owner —
      ~150 `useAppStore.getState()` reads cannot call a hook, so the store field
      has to stay.
- [x] React Query `['github-issues', projectId]` designated the single owner;
      Zustand `githubIssues` / `activeIssue` become a read-only projection.
- [x] New `subscribeIssueCacheProjection(queryClient)` — subscribes to the query

## Session 7 — Unblock the main process: async PRD attachment staging + batched ref deletion

Two performance asks: synchronous `node:fs` in PRD attachment staging (runs in the
Electron main process, attachments up to 10 MB), and `for … await` deletion loops
that could be parallel. The second half turned out to be mostly a *don't* — see
Key decisions.

### System flow — where the blocking and the serialization were

```
prd-attachments:stage  (IPC, main process)
  for each file (≤ 6, cap enforced mid-loop)
    statSync        ─┐
    openSync/readSync│  all sync → event loop frozen for the whole staging pass
    closeSync        │
    copyFileSync    ─┘
  ⇣ now
    fs.stat / fs.open→handle.read→handle.close / fs.copyFile   (fs/promises)
    + post-await guard: session may have been cleared mid-flight
  ⇣ handler
    try/catch → log.error(full) → throw new Error(clampError(err))   (repo IPC rule)

pruneWorktreeArtifacts(worktreePath)          ← genuinely independent
  15 sibling top-level dirs, node_modules dominates
  for … await fs.rm  →  Promise.all(pruneArtifact)   + nesting guard
  per-item try/catch = allSettled semantics → { removed, missing, failed }

deleteThreadCheckpointRefs / deleteAllCheckpointRefs   ← NOT independent
  for … await git update-ref -d <ref>
    every deletion takes packed-refs.lock; N processes contend on 1 lock
  ⇣ instead of Promise.all
  git update-ref -z --stdin  ←  "delete <ref>\0\0" × N     (one process, one lock)
    transaction is all-or-nothing → on failure, fall back to the per-ref loop
```

### Affected components
- **Main process / IPC** — `prd-attachments.ts`, `register-support-handlers.ts`,
  `register-project-handlers.ts`
- **Git** — `worktree-artifacts.ts` (parallelized), `checkpoint.ts` (batched)
- **Pipeline** — `execution-phases.ts` (documented as intentionally serial)

### What was done
- [x] Every `*Sync` call in PRD attachment staging converted to `fs/promises`;
      `openSync/readSync/closeSync` became `fs.open` → `handle.read` →
      `handle.close` in a `finally`.
- [x] The four `prd-attachments:*` handlers made async, each wrapping failures in
      `clampError` (first line + ~280 chars) with the full error to the
      main-process console only.
- [x] Added a post-await liveness guard — a session cleared while a copy is in
      flight now reports `Attachment session was closed` instead of writing into
      a dead session. Covered by a new test.
- [x] `pruneWorktreeArtifacts` → `Promise.all` with a `hasNestedTargets` guard and
      per-artifact outcome capture; result folding stays deterministic.
- [x] Both checkpoint ref loops → a single `update-ref -z --stdin` transaction with
      a serial fallback that preserves the best-effort contract.
- [x] Three sites documented as intentionally serial rather than changed.
- [x] `prd-attachments.test.ts` rewritten for the async API;
      `register-instant-handlers.test.ts` awaits added.
- [x] Typecheck 15/15, lint clean (1004 files), `packages/git` 108 tests,

### Key decisions
- **The ref-deletion loops are not a `Promise.all` candidate.** Git takes
  `packed-refs.lock` for *any* ref deletion, so concurrent `update-ref -d`
  processes contend on one lock with a short retry timeout and start failing —
  and the loops swallow failures, so the result would be a silent ref leak, not a
  visible error. Batching into one `update-ref -z --stdin` transaction is the real
  win: one process, one lock, one pass. Wire format verified in a throwaway repo
  before shipping.
- **`simple-git` has no stdin channel**, so `checkpoint.ts` spawns git directly in
  exactly one helper (`runGitWithStdin`) — the batch form has no argv equivalent.
- **Nesting guard on the artifact prune.** The default list is 15 siblings, but the
  function takes a caller-supplied list. If any target sits inside another,
  recursive removal of the parent races the child, so those fall back to ordered.
- **`stagePrdAttachments` stays serial.** Per-file decisions are not independent:
  each is deduped against everything already staged and counted against a cap that
  `break`s the loop. The cap is 6 files — there is nothing to win.
- **Worktree/branch removal in the pipeline stays serial**, same shared-repo-lock
  reason. Comments added so the next reader doesn't "fix" it.
- **Left one blocking read alone** — `fs.readFileSync(skillPath)` at
  `register-github-handlers.ts:1625`. Same class of problem, outside the stated
  scope, flagged rather than folded in.

## Session 9 — SIGKILL escalation was unreachable dead code

`ProcessManager.kill()` marked a process `exited` the instant it *sent* the
signal, so every downstream liveness check saw a corpse that was still running.
The pipeline's 5-second SIGKILL follow-up in `runtime-setup.ts` therefore never
fired once — a child that traps SIGTERM (`trap "" TERM`) outlived the app
forever. The `onAbort` path had no escalation at all.

### System flow — before vs after

```
BEFORE
  kill(id)
    └── send SIGTERM ──► updateState('exited')   ← lie, told synchronously
  runtime-setup: setTimeout(5s) → get(id).state === 'exited' → no SIGKILL  [DEAD]
  child ignoring SIGTERM: orphaned indefinitely

AFTER
  kill(id, signal?, { escalateAfterMs? })
    ├── send signal
    ├── updateState('terminating')          ← new intermediate state
    └── scheduleEscalation(proc, 5_000)     ← default, opt out with 0
          └── on fire: identity-check the ManagedProcess, then SIGKILL

  real pty 'exit' / child 'close'
    └── clearEscalation(id) → updateState('exited')   ← only place 'exited' is set

  runtime-setup timeout AND onAbort → terminate() → processManager.kill(id)
    (escalation owned by the manager: only it sees the real exit event and can
     cancel the pending SIGKILL — the runtime promise has already settled)
```

### Affected components
- **Shared types** — `AgentState` gains `'terminating'` (TS-only union; no zod
  schema validates it at the IPC boundary, so this is not a wire break).
- **Agents** — `process-manager.ts` (escalation timers), `cli-stdin-runner.ts`
  (its own SIGTERM → 5s → SIGKILL for one-shot CLI timeouts).
- **Pipeline** — `runtime-setup.ts` dead inline escalation removed, shared
  `terminate()` used by both timeout and abort.
- **Desktop** — `register-feature-qa-handlers.ts` treats `terminating` as "not a
  server we can hand to the user".

### What was done
- [x] Added `'terminating'` to `AgentState`; audited **every** reader of `state`
      across `packages/` and `apps/desktop/`. `write()` (`=== 'running'`),
      `listActive()`, `killAllAndWait()`, `cleanup()`, `useIpc.ts`,
      `TerminalView.tsx`, `server-lifecycle.ts` are all correct as written; only
      `resize()`, `killStalled()` and the feature-QA handler needed the new arm.
- [x] `kill()` now schedules escalation **by default** (5 s), keyed by id but

## Session 10 — execute-path git goes async

`execFileSync` on the per-node execute path froze the Electron main event loop for
the whole subprocess. `git add -A` on a large worktree is not fast, so the UI
stalled, IPC queued, and the pipeline heartbeat could not be written. The calls run
once per node *and* again per fan-out worker. `packages/git/src/checkpoint.ts`
already documented that git must be async — the execute path just never followed it.

### System flow — sync subprocess → locked async transport

```
before  (blocks the main loop for the whole git invocation)
  computeNodeDiff → execFileSync status → add -A → commit → diff
                    └── main process frozen ─────────────────┘

after
  computeNodeDiff → withGitLock(cwd, async run => {
                       status → add -A → commit → diff      ← one lock, one index
                    })
                    └── simple-git, event loop free ────────┘

withGitLock: promise queue keyed by path.resolve(cwd)
  /wt-a  ──[add]──[commit]──▶ ──[status]──▶     serialized: same index
  /wt-b  ──[add]──[commit]──▶                   parallel: distinct worktree
  chains off the previous holder's *settled* state, so one rejection
  neither poisons nor stalls the queue
```

### Affected components
- **Git package** — new `git-exec.ts` transport; `checkpoint.ts` now consumes it
- **Pipeline** — `execution-phase-utils.ts`, `execution-phases.ts`,
  `execution-shipping-phases.ts` (one callsite)
- **Main process** — the behavioural payoff; no renderer change

### What was done
- [x] Promoted `checkpoint.ts`'s private simple-git `runGit` into
      `packages/git/src/git-exec.ts` — reused the existing pattern rather than
      inventing a transport.
- [x] Added `withGitLock` (non-reentrant, per-resolved-cwd promise queue) to give
      back the stage→commit atomicity `execFileSync` provided for free.
- [x] Converted `probeWorktreeChanges`, `resolveWorktreeDiffBase`,
      `captureNodeAnchorSha`, `computeNodeDiff` and their 8 callsites.
- [x] Confirmed fan-out workers each own a distinct worktree
      (`wm.create(\`${threadId}-fan-${i+1}\`, …)`) → distinct index → safe parallelism.
- [x] Kept every original try/catch, moving the `await` inside it, so rejected
      promises are caught exactly where sync throws were.
- [x] Source-guard test: `execution-phase-utils.ts` may not contain `execFileSync`,
      `execSync`, or `child_process`.
- [x] 10 new `git-exec` tests + reworked utils tests. Pipeline 600 passed / 7
      skipped, git 117 passed, repo-wide typecheck 15/15.

### Key decisions
- **Per-cwd lock, not a global one.** `context.worktreePath ?? context.projectPath`
  means a worktree-less context falls back to the shared project repo, so a lock is
  mandatory — but keying it on the resolved path keeps fan-out workers fully
  parallel. Verified by a `peak === 2` concurrency test.
- **`withGitLock` is deliberately not reentrant.** Inside the callback you use the
  supplied `run`, never the exported `runGit`. `probeWorktreeChanges` therefore
  calls a lock-free `resolveDiffBaseWith(run, context)` body; the public
  `resolveWorktreeDiffBase` wraps that same body in its own lock. A test asserts the
  probe takes exactly one lock, guarding the self-deadlock.
- **One lock spans the whole probe.** Status and the base-vs-HEAD diff must observe
  the same index, not one straddling another caller's stage/commit.
- **Checkpoint keeps the unlocked variant.** Capture stages into an isolated
  `GIT_INDEX_FILE` and restore is off the per-node path, so neither contends for the
  real index. Importing `runGitUnlocked as runGit` left all ~20 callsites untouched.
- **Queue chains off *settled* state.** `previous.then(fn, fn)` — a rejected
  sequence must not poison or stall the next holder.
- **Used the existing async `resolveCurrentBranch`.** The related shared
  `getCurrentBranch` task has not landed, and none of the in-scope calls were
  `rev-parse --abbrev-ref HEAD`, so there is no collision either way.
- **Did not widen scope** to the remaining sync git in the verify/shipping path
  (`execution-phases.ts` ~1561-1598, all of `execution-shipping-phases.ts`). Same

## Session 11 — Memoize list-view rows so the 5s issue poll stops re-rendering the board

List view (`IssueListView`) re-rendered every row on every 5-second issue poll.
Its direct counterpart in card view (`DraggableCard`) has been memoized all along —
the list row was a single missed instance of the same pattern.

### System flow — why the poll reached the rows

```text
IssuesPanel
  useQuery(['github-issues', projectId], staleTime: 5_000)
    → poll settles every 5s → IssuesPanel re-renders
       │  React Query structural sharing keeps unchanged issue objects identical,
       │  so `issues` entries are referentially stable across polls…
       ↓
    KanbanBoard
      badge/staleness Maps already useMemo'd on boardIssues
      onIssueClick / onOpenPullRequest / onArchiveIssue passed straight through
       ↓
    IssueListView → getListRowProps(issue, …) → DraggableListRow
       ✗ not memoized      → every row re-renders unconditionally
       ✗ callbacks unstable → memo alone would have been decorative
```

Both halves had to change: the memo, and the parent handlers feeding it.

### Affected components
- **UI package** — `packages/ui/src/kanban-board/IssueListView.tsx`
- **Desktop renderer** — `apps/desktop/src/renderer/components/IssuesPanel.tsx`

### What was done
- [x] Wrapped `DraggableListRow` in `memo()` following `DraggableCard` exactly —
      plain `memo`, default shallow compare, `Component` suffix on the inner
      function, explicit `displayName`.
- [x] Audited every sibling in `packages/ui/src/kanban-board/`: `DraggableCard` was
      the only memoized component; the rest (`DroppableColumn`, `StackedColumn`,
      `SectionBlock`, `ListSectionBlock`, `ColumnHeader`, `BoardToolbar`,
      `HiddenColumnsPanel`) are containers taking rebuilt Maps, not per-issue leaves.
      The list row was the single instance of the asymmetry.
- [x] Stabilized the three handlers that reach the row in `IssuesPanel`:
      `handleIssueClick` and `handleIssueComment` wrapped in `useCallback`; the
      inline `onOpenPullRequest` and `onArchiveIssue` arrows hoisted into
      `useCallback` handlers.
- [x] Added `IssueListView.memo.test.tsx` — a render-count instrument, not a
      smoke test. `formatDate` is called exactly once per row render and nowhere
      else in the file, so a spy on it counts row renders precisely.
- [x] ui 245/245, ui + desktop typecheck clean, desktop 1596/1597 (the one failure
      is the documented macOS `/var` symlink issue from #488).

### What was measured

`formatDate` spy call counts across a parent re-render, 3 rows:

| scenario | before | after |
|---|---|---|
| poll settles with identical data | 3 / 3 rows | **0 / 3** |
| one issue's title changes | 3 / 3 rows | **1 / 3** |
| a callback prop gets a fresh identity | 3 / 3 | 3 / 3 (guard test) |

The third row of the table is deliberate: it fails if anyone reintroduces an
inline arrow in the parent, which is the failure mode that would silently make
the memo decorative again.

### Key decisions
- **Plain `memo`, no custom comparator.** `DraggableCard` uses default shallow
  compare; the instruction was to match it exactly. A custom comparator would also
  have to be maintained against 14 props.
- **Stabilized only the handlers that reach the memoized row.** `onOpenExternal` is
  an identical inline arrow but only reaches `BoardToolbar` / `ProjectLinks`, which
  are not memoized — wrapping it would buy nothing and widen the diff.
- **Left badge-object churn alone.** The badge Maps are memoized on `boardIssues`,
  so when *any* issue changes, every non-null badge object is rebuilt and rows
  carrying badges still re-render. Rows with all-null badges (the common case)
  are unaffected. Fixing it needs per-issue badge identity caching (WeakMap or
  similar) — machinery that exists nowhere else in this codebase. Noted as
  follow-up rather than invented here.
