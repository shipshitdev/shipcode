## Session 1 - Setup Affordances, Loading States, Badge Cleanup, and Clarification State

**Status:** Complete (targeted tests/typechecks green)

### Context

This session started from several live UI affordance issues found while using the desktop app:

- the detected setup profile chip looked clickable but did nothing
- async submit buttons, including `Re-detect`, did not consistently disable or show stable-width loading state
- recent activity rows could look clickable even when no navigation target existed
- running-agent/model badges were too verbose (`Codex / GPT-5.4`)
- revision badges used `REV` text where the number alone was enough
- after answering a planner clarification and resuming planning, Issue Detail still showed the open questionnaire instead of only the submitted answers

The final state now separates pending clarification from answered clarification in persisted thread state instead of relying on renderer-only filtering.

### System Flow - Clarification Answering

```text
thread.status = clarifying
thread.clarificationRequest = pending request
          |
          v
User answers in Issue Detail
          |
          v
pipeline:answer-clarification
          |
          v
ThreadQueries.resolveClarification(...)
          |
          +--> clears pending clarification_request / clarification_answers
          |
          +--> stores answered_clarification snapshot
          |
          v
pipeline.startPlanGeneration(...)
          |
          v
Issue Detail renders read-only submitted answers
instead of the pending questionnaire
```

### Key Decisions

| Decision | Rationale |
|----------|-----------|
| Use an explicit `answeredClarification` snapshot | Pending questions and submitted answers are different states; overloading `clarificationRequest` made the UI ambiguous |
| Clear pending clarification immediately on answer submit | The renderer should not have to infer that a non-clarifying thread with `clarificationRequest` is no longer pending |
| Keep the answered snapshot after planning resumes | Users should be able to see what they submitted while the resumed planning pass is running |
| Keep model badges provider-free in compact card surfaces | The model and effort are the useful signal; provider adds width and repeats implied routing detail |
| Put revision meaning in the tooltip | The chip can stay compact while still explaining what the number represents |
| Use one shared loading-content helper | Prevents spinner insertion from resizing buttons differently across surfaces |

## Session 3 — Approval vs Execution-Slot UX Cleanup

**Status:** Complete for the targeted UX cleanup. Targeted tests, `packages/ui` typecheck, shared build, and Biome are green. `apps/desktop` typecheck still fails on an unrelated `@shipcode/agents` export issue.

### Context

This session cleaned up the remaining confusion around the internal `awaiting_approval` phase.

The backend intentionally keeps approved threads in `awaiting_approval` while they wait for an execution slot, but several renderer surfaces still presented that as if a human approval was missing. The goal was to make every user-facing surface distinguish:

- **Needs approval**: human action still required
- **Waiting For Execution / Waiting for slot**: approval is already done; runtime is only waiting for capacity

### System Flow

```text
thread.status = awaiting_approval
          |
          v
latest plan status?
          |
   +------+------+
   |             |
   v             v
awaiting_approval   approved
   |             |
   v             v
Needs approval       Waiting For Execution
human gate           execution-capacity wait
```

### What Was Done

- [x] Added `latestPlanStatusByThreadId` to `ThreadPanelData` and used it to identify approved slot-waiters in the board.
- [x] Split approved slot-waiters into **Agent Loop → Waiting For Execution** instead of leaving them under human approval.
- [x] Excluded approved slot-waiters from `Needs approval` filtering and pending approval counts.
- [x] Added runtime-capacity copy to Project Settings so execution-slot limits are visible from the project workflow screen.
- [x] Normalized approval copy across Inbox, OS notifications, chat notifications, settings toggles, Issue Detail plan history, and the shared pipeline status step.
- [x] Removed the redundant Inbox `Approval required` badge in favor of one `Needs approval` state label.
- [x] Fixed Terminal drawer labels:
  - human approval wait now reads `Needs approval`
  - approved slot-waiters now read `Waiting for execution slot`
  - the header chip now reads `Waiting for slot`
- [x] Fixed Command Palette actions so approved slot-waiters no longer show `Approve Plan` / `Reject Plan`; they show disabled `Waiting for execution slot` instead.
- [x] Fixed Mission Control running cards so approved slot-waiters render `Waiting for slot`.
- [x] Rebuilt `@shipcode/shared` so downstream desktop typecheck sees `ActivePipelineSummary.approvedAwaitingExecution`.
- [x] Updated docs for Inbox, Kanban, Mission Control, Settings, Terminal, and Pipeline Overview.

### Key Decisions

| Decision | Rationale |
|----------|-----------|
| Keep the backend phase machine unchanged | Queue-drain and restart behavior already rely on `awaiting_approval` + latest approved plan status; a state-machine rewrite would be broader and riskier |
| Use latest plan status to disambiguate UI | `thread.status` alone cannot tell “needs approval” apart from “already approved, waiting for capacity” |
| Keep `queued` reserved for pre-agent queueing | Post-approval slot wait is a different user-facing state and needs different messaging |
| Hide approval actions in Command Palette after approval | Showing approve/reject after approval is materially wrong, not just unclear |

## Session 4 - Terminal Observability, Memory Cleanup, Board Safety, and Scheduler Architecture

**Status:** Complete for targeted fixes. Focused tests and typechecks are green after rebuilding dependent packages.

### Context

This session came from live app usage while pipelines were running against real GitHub issues.

The main complaints were practical:

- the Console drawer looked like a narrow document column instead of a full-width terminal surface
- failed tool rows only said `Tool failed / Exit 1`, hiding the actual stderr/stdout that explains the failure
- `context` vs `memory` naming was confusing, and legacy `.agents/context` support was not worth keeping pre-release
- failed Kanban cards used a harsher solid background than the nicer glass treatment used by `DONE`
- approval confirmation could look like a dead click when a plan was already approved but waiting for an execution slot
- card click-to-open conflicted with drag/drop, and accidental `Done` moves were too easy to make permanent
- the architecture had duplicated scheduler logic and duplicated thread/issue phase-sync paths

### System Flow - Updated Scheduler and Phase Sync

```text
github:start-issue / queued issue promotion
              |
              v
       PipelineScheduler
              |
     +--------+---------+
     |                  |
     v                  v
 queue if full      launch issue
                        |
                        v
              pipeline.startFromGitHubIssue(...)
                        |
                        v
              pipeline phase transitions
                        |
                        v
              syncThreadAndIssuePhase(...)
                        |
              +---------+----------+
              |                    |
              v                    v
        threads.status     github_issue_cache.pipeline_status
```

### Key Decisions

| Decision | Rationale |
|----------|-----------|

### Key Decisions

| Decision | Rationale |
|----------|-----------|
| Use app-specific launcher commands | Generic `open -a <terminal> <path>` is not reliable for terminal working-directory behavior |
| Surface launcher errors in the renderer | A failed external app launch should be visible immediately, not look like a dead click |
| Keep the tab strip as navigation only | Refresh/edit are Issue-content actions, not global tab-bar actions |
| Use fullscreen icons for full-size Issue Detail | Panel-left icons implied sidebar toggling; maximize/minimize matches the actual action |
