## Session 2 — Grok Build (Grok 4.5) as a first-class execute-only executor

### Context
- User: "do we have any issue about the grok integration. it needs to be done ASAP." + earlier: "we will use grok 4.5 from the cli once available in europe."
- No existing issue → created **#326** (implementation-ready spec), then built it directly (chosen over routing to Codex: local Codex CLI is misconfigured — defaults to gpt-5.6-sol/max the 1.0.3 binary can't serve — and the `codex:codex-rescue` agent type dropped out on session resume).
- Branch `claude/grok-executor-integration`, based on the #325 tip (inherits the Fable/GPT-5.6 catalog it builds on).

### Load-bearing design decision
- **Execute-only, mirroring Cursor.** Confirmed via xAI headless docs: Grok Build's `-p` mode has **no read-only sandbox** flag (only `--always-approve` auto-write). It therefore must not drive plan/review/verify (which the pipeline treats as read-only), or it could mutate the worktree. Added to `EXECUTOR_PHASE_PROVIDERS`, not `VALID_PHASE_PROVIDERS`.

### System flow
```text
AgentType/ExecutorModel += 'grok'
  ├─ model-catalog: GROK_FALLBACK_MODEL_IDS/OPTIONS (grok-4.5), PINNED_MODEL_DEFAULTS.grok, aliases (grok/grok-4.5/grok4.5)
  ├─ model-display: PROVIDER_DISPLAY.grok='Grok', GROK_MODEL_PATTERN /^grok/i, inference branch
  ├─ model-resolution: asExecutorModel + EXECUTOR_PHASE_PROVIDERS (execute-only)
  ├─ reasoning-effort: GROK_REASONING_EFFORTS=['none'] (CLI exposes no effort knob, mirrors cursor)
  ├─ cli-model-capabilities: grok fallback branch + 'Grok CLI' labels
  ├─ constants.PIPELINE_EXECUTOR_PROVIDERS += grok; types/health SystemHealth.grok?
  ├─ agents: grok-cli-provider.ts (execute-only, `grok -p --output-format json --no-auto-update [--model] [--always-approve]`, stdin prompt), providers/index export, registry grok case, AgentProvider id 'grok-cli'
  ├─ health-check: checkGrokAuth (XAI_API_KEY / `grok auth status`), checkGrokModelCapabilities, wired into all capability + system-health aggregators
  └─ apps: desktop main registry + CLI context registry; renderer model-provider-options-data (PROVIDER_DISPLAY.grok='xAI', getModelOptions branch)
```

### Key decisions / assumptions (flagged in PR for verification against the live CLI)
- **Prompt piped on stdin** (like cursor/gemini) rather than as a positional arg — headless docs are pipe/CI-oriented; adjust if the installed CLI requires a positional.
- **`grok auth status`** is a best-effort probe that fails closed (reports unauthenticated) if the subcommand differs; `XAI_API_KEY` is the definitive headless signal.
- **Registered in apps/cli too** (diverges from cursor/gemini, which the CLI omits) because the user explicitly wants Grok "from the cli". Trivially revertible.
- Not added to the automation modal (execute-only, matches cursor/gemini which aren't offered there). Not a project-open target (that's Cursor-the-IDE, unrelated).
- Grok can't be verified end-to-end until EU access (~mid-July); merges now behind the provider abstraction. OpenRouter already accepts `x-ai/grok-4.5` free-text, unchanged.

## Session 3 — Issue #212: ShipCode-owned checkpoint refs (feature-implementation routine, Fable 5)

### System flow

```text

  → claim: assign VincentShipsIt, board → In Progress, branch issue-212-checkpoint-refs
  → recon: 1 Workflow reader (desktop map) + inline reads (pipeline/db/git surfaces)
  → new packages/git/src/checkpoint.ts (capture/restore/list/delete via temp GIT_INDEX_FILE)
  → db migration v64 (pipeline_checkpoints.ref_name) + queries + shared PipelineCheckpoint.refName
  → pipeline: pre-execute + post-attempt ref capture in execution-phases.ts
  → desktop: ref-backed checkpoint:restore + stale-ref pruning + teardown cleanup
  → resume context diffs prefer checkpoint ref (register-pipeline-handlers.utils.ts)
  → scoped tests + typecheck + biome + adversarial verify Workflow → PR
```

### Affected components

- `packages/git` — new `checkpoint.ts` (+ real-git integration tests, a first for this package), exports.
- `packages/db` — `migrateV64` (`ref_name TEXT` on `pipeline_checkpoints`), `CheckpointQueries` plumbing.
- `packages/shared` — `PipelineCheckpoint.refName`.
- `packages/pipeline` — `execution-phases.ts`: pre-execute rows now carry a ref; new `after_execute` capture after every execute/node attempt (best-effort, never fails the phase).
- `apps/desktop` — `checkpoint:restore` uses the ref when present (falls back to commit SHA), prunes refs newer than the restored turn, clampError-wrapped; `cleanupTrackedWorktrees` deletes all repo checkpoint refs; `git:cleanup-apply` deletes refs for threads whose worktrees were removed; resume-context diff base prefers the ref; restore confirm copy reflects snapshot semantics.

### What was done

- [x] Ref layout `refs/shipcode/checkpoints/<threadId>/turn/<n>`, ShipCode author identity, local-only.
- [x] Capture: temp `GIT_INDEX_FILE` under the git common dir (`read-tree HEAD` → `add -A` → `write-tree` → `commit-tree -p HEAD` → `update-ref`); real index/branches/tags/stash untouched (tested).
- [x] Restore: `reset --hard <ref parent>` → `clean -fd` → `restore --source <ref> --worktree --staged -- .` → mixed reset. Reproduces modified/deleted/untracked state, removes post-checkpoint files (tested; semantics verified empirically in a scratch repo before writing the module).
- [x] Verification: per-package tests (git 7, db 2+77 schema, pipeline 198+46, desktop 65+94+21+28) one file at a time; typecheck green on shared/git/db/pipeline/desktop; biome clean.

### Key decisions

- **Restore intentionally unstages everything** (index = HEAD after restore) per the issue's "unstage/reset as needed" — staged-vs-unstaged distinction at capture time is not preserved, file content is.
- **`WorktreeManager.remove` untouched** (memory rule: concrete values only). Ref cleanup lives with callers: `cleanupTrackedWorktrees` (project remove/archive) and the `git:cleanup-apply` handler (worktreePath→thread cross-reference, since `CleanupItem` has no threadId).
- **Capture failures degrade, never block**: pre-execute falls back to a metadata-only row (`refName: null`); post-attempt capture failure just logs.
- **Known gap (documented in PR)**: instant-thread raw `DELETE` cleanup (`threads.deleteOlderThan`) bypasses all worktree/ref hooks — instant threads don't run the execute phase today, so no refs exist for them.
- Real-git integration tests introduced in `packages/git` (mkdtemp repos) because checkpoint semantics are untestable with the package's existing mocked-simple-git pattern.

## Session 5 — Unify GitHub pipeline sync (closes #333 + #334)

### Context

Follow-up to Session 4's audit. Four issues were filed (#331–#334). #333 (manual-transition
ghSync gap) and #334 (duplicate label-sync) turned out to be **one refactor**: a correct #333
requires a shared queued sync reachable from the desktop layer, which is exactly #334's
deliverable. Splitting them would ship a knowingly-racy #333 and then rip it out. Combined into
one PR (`fix/unify-gh-pipeline-sync`). #331 and #332 remain separate, pending.

### System flow

```text
Before: THREE label/status writers, no shared serialization
  ├─ performGhSync (runtime.ts) → private GhSyncQueue          [queued]
  ├─ syncIssuePipelineLabel (github-pipeline-label-sync.ts)    [unqueued, dup logic]
  └─ inline block (helpers.ts) + transitionThreadPhase → NO ghSync at all  ← #333 gap

After: ONE shared service, ONE queue, per-issue keyed
  createGhSyncService({getProject}) [packages/pipeline/src/gh-sync.ts]
    owns one GhSyncQueue(performGhSync)
    exposes { enqueue, deps: GhSyncDeps }
  desktop index.ts builds ONE instance →
    injected into createPipeline deps (runtime shares it)
    + every transitionThreadPhase call (#333 fixed)
    + PipelineScheduler deps (4 sites) + registerIpcHandlers + github handlers (#334)
  github-pipeline-label-sync.ts DELETED
```

### Affected components

- `packages/pipeline` — new `gh-sync.ts` (`createGhSyncService`, extracted `performGhSync`
  verbatim), exported from `index.ts`; `PipelineDeps.ghSync?: GhSyncService` (`types.ts`);
  `runtime.ts` uses `deps.ghSync ?? createGhSyncService(...)` fallback and enqueues on the
  shared service (was a private queue).
- `apps/desktop` — `index.ts` constructs the singleton and injects it everywhere;
  `transitionThreadPhase` (`helpers.ts`) takes `ghSync?: GhSyncDeps` and passes it to
  `syncThreadAndIssuePhase` (closes #333); `github-pipeline-label-sync.ts` deleted, all callers
  (`register-github-handlers.ts`, `pipeline-scheduler.ts`, `helpers.ts`) migrated to the shared
  service (closes #334); scheduler `_syncPipelineLabel` takes `Project` + routes through
  `this.deps.ghSync`.

### Key decisions

- **Combined #333+#334** — one seam, not two. Optional `ghSync?` params keep the pipeline
  package standalone/test-friendly; every real desktop call site passes the singleton (verified
  all 10 `transitionThreadPhase` + 4 `PipelineScheduler` sites).
- **Single per-issue queue** so runtime + manual + refresh writes for one issue serialize and
  coalesce — the race #333/#334 warned about is structurally gone.
- **Intended behavior change:** `syncCachedIssuePipelineLabel` (helpers) and scheduler
  `_syncPipelineLabel` were label-only; routed through the shared service they now ALSO write
  the Projects v2 Status field when the project has a configured board. This is the point of
  consolidation, not a regression.
