## Session 1 — reconciliation loop could overlap itself and double-cancel

`createReconciliationLoop.start()` scheduled `tick()` on a bare `setInterval`
with no re-entrancy guard. A tick issues **one sequential `gh issue view` per
active thread**, so a slow GitHub pushes it past `intervalMs`, the next firing
starts while the previous is still walking the thread list, and both observe the
same closed issue and call `pipeline.cancel(threadId)`.

The duplicate cancel is not a no-op — it can land on a *different run than the
one it meant to kill*.

### System flow — how the second cancel hits a live run

```
t=0ms     interval fires → tick A starts
            listActive() → [t1 (issue #42)]
            await gh issue view 42 ................. GitHub is slow
t=30000   interval fires → tick B starts (BEFORE the guard: nothing stops it)
            listActive() → [t1]  (t1 is still active — A hasn't cancelled yet)
            await gh issue view 42 ................. also slow

t=31000   tick A resolves: state === 'closed'
            → pipeline.cancel('t1')      → run R1 finished, thread idle
            → onReconciliationCancel('t1') → worktree cleanup, slot freed

t=31500   thread t1 is relaunched (retry scheduler / user / issue reopened)
            → activePipelines['t1'] = { runId: R2 }

t=32000   tick B resolves: state === 'closed'   ← STALE observation from t=30000
            → pipeline.cancel('t1')
                finishCurrentRun() re-resolves the runId FROM THE DB:
                  activePipelines.get('t1')?.runId  →  R2   ← the NEW run
                → pipelineRuns.finish(R2, 'cancelled')
                → haltActivePipeline → emitPhase('t1','idle')
            → R2 is dead. It never ran. Nothing logged it as wrong.
```

The stale read is the whole bug: tick B decided "cancel" against a world that no
longer exists by the time it acts.

### Affected components

- `packages/pipeline/src/reconciliation-loop.ts` — the fix
- `packages/pipeline/src/pipeline.ts` — `finishCurrentRun` / `haltActivePipeline`,
  the downstream that turns a duplicate cancel into a killed live run. **Not
  touched this session.**

### Key decisions

- **Guard in the scheduler callback, not inside `tick()`.** `tick()` is exported
  as "exposed for testing" and every existing test calls it directly; guarding
  inside it would make direct calls silently return an empty result. Overlap only
  arises from the interval, so that is where the guard belongs.
- **`.finally()` clears the flag, not `.then()`.** A thrown tick must not leave
  `inFlight` set — that would permanently wedge the loop after one transient
  GitHub failure. There is a test for exactly this.
- **Did not batch the `gh` calls.** Out of scope and not trivial: `gh issue view`
  is one-issue-per-invocation, so real batching means a GraphQL rewrite of
  `IssueStateProvider`. The false comment is now honest about the cost instead.
- **Did not fix the `finishCurrentRun` runId re-resolution.** This PR closes the
  reconciliation loop as a *source* of duplicate cancels; the downstream hazard
  survives for any other duplicate-cancel path. Left as follow-up rather than
  widening a MEDIUM bugfix into a `cancel()` semantics change.

### Files changed

`packages/pipeline/src/reconciliation-loop.test.ts`.

### Mistakes and fixes

- **The guard broke an existing green test — and the test was the thing at
  fault.** `start() schedules ticks and stop() clears them` advanced fake timers
  twice with no `await` in between, so tick 1's promise had never settled when
  firing 2 landed and the guard correctly skipped it. Real elapsed wall-clock
  always drains the microtask queue, so the scenario the test encoded cannot
  happen in production. Added an `await` between advances. Worth stating plainly:
  the first instinct on a newly-red pre-existing test is to soften the new code —
  here that would have deleted the fix.
- **Only `setInterval`/`clearInterval` are faked** in this suite
  (`vi.useFakeTimers({ toFake: [...] })`), so `setTimeout` is real and
  `await new Promise(r => setTimeout(r, 0))` is a working microtask flush. Any
  new async test here depends on that; do not widen `toFake` without checking.
- **The package is `@shipcode/pipeline`, not `@shipshitdev/pipeline`.** The
  published CLI is `@shipshitdev/shipcode`; internal packages are all
  `@shipcode/*`. A turbo `--filter` on the wrong scope matches nothing and exits
  0 — it looks like a pass.

## Session 2 — unguarded `git rev-parse HEAD` in `startVerification`

The verification phase ran six `execFileSync` git calls in one block. Five were
guarded; the `rev-parse HEAD` that resolves `context.verifiedSha` was not. A
deleted worktree or a corrupt repo made it throw straight out of the phase
handler, past the handler's own failure path.

### System flow — where the throw went

```
startVerification(threadId)
  ├─ try { status --porcelain / add -A / commit }   ← guarded
  │    catch → console.error + emitPhase('failed') + activePipelines.delete()
  │             → return { next: 'failed' }          ← phase-local cleanup runs
  │
  ├─ rev-parse HEAD                                  ← UNGUARDED (before)
  │    throw ─────────────────────────────────────┐
  │                                               │
  └─ try { diff base..head } catch → diff = ''    │  ← guarded
                                                  │
                                                  ▼
                        pipeline.ts `launch()` generic catch
                          console.error('dispatch loop crashed')
                          runtime.emitPhase('failed', <git error>)
                          activePipelines.delete()

  Message reaching the renderer was clamped (emitPhase clamps), but it read
  "Command failed: git rev-parse HEAD" — no indication the *verification phase*
  was what died — and the failure was reported as a dispatch-loop crash rather
  than a phase failure.
```

### Affected components
- **Pipeline** — `packages/pipeline/src/pipeline/execution-phases.ts`
  (`startVerification`)
- **Tests** — `packages/pipeline/src/pipeline/execution-phases.test.ts`

### What was done
- [x] Wrapped the `rev-parse HEAD` call in the same catch shape the
      pre-verification commit block above it uses: capture the message,
      `console.error` it with the thread id, `emitPhase(threadId, 'failed', …)`,
      `activePipelines.delete(threadId)`, `return { next: 'failed' }`.
- [x] Added a regression test: `rev-parse` throws with a 300-frame stack, and the
      phase resolves `{ next: 'failed' }` instead of rejecting, cleans
      `activePipelines`, and emits a message whose clamped form keeps the
      phase-identifying prefix and drops the stack tail.
- [x] `@shipcode/pipeline` suite green (608 passed / 7 skipped, 28 files);
      `turbo run typecheck` clean across all 15 tasks.

### Key decisions
- **Matched the neighboring catch, did not introduce a new error shape.** The
  commit block directly above uses bare `error.message` and relies on
  `runtime.emitPhase` for the clamp (`runtime.ts:820`). Calling `clampError` at
  this site would have double-clamped and diverged from the block's five other
  calls for no behavioral gain.
- **Prefix-first message.** `emitPhase` clamps to first line + 280 chars, so
  `Verification could not resolve HEAD: <git message>` survives the clamp with
  the useful part intact. The test asserts that property rather than asserting
  clamping itself, which `emitPhase` already owns.
- **Left the block synchronous.** `git add -A` and `git commit` here can block
  the Electron main event loop on a large worktree, but the async-transport
  migration is its own concern (execute path already moved in #518). Kept this
  change to the guard.

### Files changed
- `packages/pipeline/src/pipeline/execution-phases.ts` — guarded the HEAD lookup
- `packages/pipeline/src/pipeline/execution-phases.test.ts` — regression test

### Next steps

## Session 3 — TOCTOU race let two launches start the same thread

`launchIssuePipeline` guarded re-launch on `thread.status` alone. The pipeline's
`activePipelines` map — the thing that actually knows a thread is running — is
only populated later, inside `ensureContext`. Everything between the status read
and that point is awaited I/O, so two launches for the same `threadId` could both
read a reusable status and both proceed. Flagged by CodeRabbit on PR #501,
confirmed pre-existing.

### System flow — where the window was

```
launchIssuePipeline(issue)
  read linkedThread.status ∈ REUSABLE_THREAD_STATUSES   ← CHECK
    │
    ├─ await hooks.onIssueLinked()        (renderer refresh)   ┐
    ├─ await validatePhaseModels()        (model resolution)   │  window
    ├─ await GitHub synthesis             (quick tasks only)   │  open
    │                                                          ┘
    └─ startFrom*() → bootstrapPipelineRun()
         → contextHelpers.ensureContext(threadId, …)           ← USE
             activePipelines.set(threadId, ctx)

  a second launch entering anywhere above passes the same CHECK
    → two pipelines, one thread, one worktree
```

The fix closes the window by claiming the thread **before the first `await`**:

```
activePipelines   ← threads with a live context (existing)
launchReservations ← threads whose launch is in flight (new)

reserveLaunch(id) = !(activePipelines.has(id) || launchReservations.has(id))
                    && launchReservations.add(id)
```

One union guard, two backing collections — not a parallel mechanism.

### Affected components
- **Pipeline** — `packages/pipeline/src/pipeline.ts` (`launchReservations`,
  `reserveLaunch`, `releaseLaunch`), `packages/pipeline/src/types.ts` (`Pipeline`
  interface)
- **Launcher** — `packages/pipeline/src/issue-launch.ts` (the fix)
- **Tests** — `issue-launch.test.ts`, `pipeline.test.ts`,
  `reconciliation-loop.test.ts`, `apps/desktop/src/main/pipeline-scheduler.test.ts`,
  `apps/desktop/src/main/ipc/register-github-handlers.test.ts`

### What was done
- [x] Added `launchReservations: Set<string>` alongside `activePipelines`, with
      `reserveLaunch` / `releaseLaunch` exposed on the `Pipeline` interface.
- [x] Claimed the thread synchronously at the top of `launchIssuePipeline`, before
      any awaited work; duplicate claims throw the existing
      `` `${label} already has active thread` `` shape.
- [x] Released the claim in a `finally`, and again in the inner `catch` *before*
      `onLaunchError` runs — that hook transitions the thread back to a
      relaunchable status, so the claim has to be gone first.
- [x] Claimed freshly created threads too, so the pipeline's view of in-flight
      launches is complete.
- [x] Concurrency test: two launches racing across a promise-gated
      `validatePhaseModels`; second rejects, `updatePipelineStatus` / `linkThread`
      each fire once, first still resolves after the gate opens.
- [x] Release tests: a failed launch frees the thread for a retry, and a successful
      launch hands off with an empty reservation set.
- [x] Converted the test doubles from constant stubs to real `Set`-backed
      implementations — a stub that always grants would hide a leak.
- [x] `@shipcode/pipeline` 614 passed / 7 skipped, `@shipcode/desktop` 1637 passed,
      typecheck 15/15, Biome clean.

### Key decisions
- **Released after success, not kept.** Keeping the reservation past dispatch would
  leak: once a run completes, `activePipelines` drops the thread and its status
  becomes reusable, so a stale claim would block every legitimate relaunch forever.
  The release is a hand-off rather than a gap — `bootstrapPipelineRun` is the first
  statement of both `startFrom*` entry points and seeds `activePipelines`
  synchronously, so the guard is already covered by the time the launcher unwinds.
- **A separate `Set`, not an early `activePipelines` seed.** Seeding a placeholder
  context looked tidier but `ensureContext` resolves the workflow policy from
  `seed.worktreePath ?? seed.projectPath` and later merges
  `seed.workflowPolicy ?? existing.workflowPolicy` — reserving with only a project
  path would pin the wrong policy for the life of the run.
- **`finally` over per-exit releases.** Synchronous throws from `updateIssueContent`
  and `setGithubIssue`, and a rejected `onIssueLinked`, all sit outside the inner
  try/catch; only a `finally` covers them without stranding a claim.
