# 2026-08-02

## Session 1 — reconciliation loop could overlap itself and double-cancel

`createReconciliationLoop.start()` scheduled `tick()` on a bare `setInterval`
with no re-entrancy guard. A tick issues **one sequential `gh issue view` per
active thread**, so a slow GitHub pushes it past `intervalMs`, the next firing
starts while the previous is still walking the thread list, and both observe the
same closed issue and call `pipeline.cancel(threadId)`.

The duplicate cancel is not a no-op — it can land on a *different run than the
one it meant to kill*.

### System flow — how the second cancel hits a live run

```
t=0ms     interval fires → tick A starts
            listActive() → [t1 (issue #42)]
            await gh issue view 42 ................. GitHub is slow
t=30000   interval fires → tick B starts (BEFORE the guard: nothing stops it)
            listActive() → [t1]  (t1 is still active — A hasn't cancelled yet)
            await gh issue view 42 ................. also slow

t=31000   tick A resolves: state === 'closed'
            → pipeline.cancel('t1')      → run R1 finished, thread idle
            → onReconciliationCancel('t1') → worktree cleanup, slot freed

t=31500   thread t1 is relaunched (retry scheduler / user / issue reopened)
            → activePipelines['t1'] = { runId: R2 }

t=32000   tick B resolves: state === 'closed'   ← STALE observation from t=30000
            → pipeline.cancel('t1')
                finishCurrentRun() re-resolves the runId FROM THE DB:
                  activePipelines.get('t1')?.runId  →  R2   ← the NEW run
                → pipelineRuns.finish(R2, 'cancelled')
                → haltActivePipeline → emitPhase('t1','idle')
            → R2 is dead. It never ran. Nothing logged it as wrong.
```

The stale read is the whole bug: tick B decided "cancel" against a world that no
longer exists by the time it acts.

- `packages/pipeline/src/pipeline.ts` — `finishCurrentRun` / `haltActivePipeline`,

### Key decisions

- **Guard in the scheduler callback, not inside `tick()`.** `tick()` is exported
  as "exposed for testing" and every existing test calls it directly; guarding
  inside it would make direct calls silently return an empty result. Overlap only
  arises from the interval, so that is where the guard belongs.
- **`.finally()` clears the flag, not `.then()`.** A thrown tick must not leave
  `inFlight` set — that would permanently wedge the loop after one transient
  GitHub failure. There is a test for exactly this.
- **Did not batch the `gh` calls.** Out of scope and not trivial: `gh issue view`
  is one-issue-per-invocation, so real batching means a GraphQL rewrite of
  `IssueStateProvider`. The false comment is now honest about the cost instead.
- **Did not fix the `finishCurrentRun` runId re-resolution.** This PR closes the
  reconciliation loop as a *source* of duplicate cancels; the downstream hazard
  survives for any other duplicate-cancel path. Left as follow-up rather than
  widening a MEDIUM bugfix into a `cancel()` semantics change.

### Mistakes and fixes

- **The guard broke an existing green test — and the test was the thing at
  fault.** `start() schedules ticks and stop() clears them` advanced fake timers
  twice with no `await` in between, so tick 1's promise had never settled when
  firing 2 landed and the guard correctly skipped it. Real elapsed wall-clock
  always drains the microtask queue, so the scenario the test encoded cannot
  happen in production. Added an `await` between advances. Worth stating plainly:
  the first instinct on a newly-red pre-existing test is to soften the new code —
  here that would have deleted the fix.
- **Only `setInterval`/`clearInterval` are faked** in this suite
  (`vi.useFakeTimers({ toFake: [...] })`), so `setTimeout` is real and
  `await new Promise(r => setTimeout(r, 0))` is a working microtask flush. Any
  new async test here depends on that; do not widen `toFake` without checking.
- **The package is `@shipcode/pipeline`, not `@shipshitdev/pipeline`.** The
  published CLI is `@shipshitdev/shipcode`; internal packages are all
  `@shipcode/*`. A turbo `--filter` on the wrong scope matches nothing and exits
  0 — it looks like a pass.
