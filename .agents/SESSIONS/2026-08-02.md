# 2026-08-02

## Session 1 — TOCTOU race let two launches start the same thread

`launchIssuePipeline` guarded re-launch on `thread.status` alone. The pipeline's
`activePipelines` map — the thing that actually knows a thread is running — is
only populated later, inside `ensureContext`. Everything between the status read
and that point is awaited I/O, so two launches for the same `threadId` could both
read a reusable status and both proceed. Flagged by CodeRabbit on PR #501,
confirmed pre-existing.

### System flow — where the window was

```
launchIssuePipeline(issue)
  read linkedThread.status ∈ REUSABLE_THREAD_STATUSES   ← CHECK
    │
    ├─ await hooks.onIssueLinked()        (renderer refresh)   ┐
    ├─ await validatePhaseModels()        (model resolution)   │  window
    ├─ await GitHub synthesis             (quick tasks only)   │  open
    │                                                          ┘
    └─ startFrom*() → bootstrapPipelineRun()
         → contextHelpers.ensureContext(threadId, …)           ← USE
             activePipelines.set(threadId, ctx)

  a second launch entering anywhere above passes the same CHECK
    → two pipelines, one thread, one worktree
```

The fix closes the window by claiming the thread **before the first `await`**:

```
activePipelines   ← threads with a live context (existing)
launchReservations ← threads whose launch is in flight (new)

reserveLaunch(id) = !(activePipelines.has(id) || launchReservations.has(id))
                    && launchReservations.add(id)
```

One union guard, two backing collections — not a parallel mechanism.

### Key decisions
- **Released after success, not kept.** Keeping the reservation past dispatch would
  leak: once a run completes, `activePipelines` drops the thread and its status
  becomes reusable, so a stale claim would block every legitimate relaunch forever.
  The release is a hand-off rather than a gap — `bootstrapPipelineRun` is the first
  statement of both `startFrom*` entry points and seeds `activePipelines`
  synchronously, so the guard is already covered by the time the launcher unwinds.
- **A separate `Set`, not an early `activePipelines` seed.** Seeding a placeholder
  context looked tidier but `ensureContext` resolves the workflow policy from
  `seed.worktreePath ?? seed.projectPath` and later merges
  `seed.workflowPolicy ?? existing.workflowPolicy` — reserving with only a project
  path would pin the wrong policy for the life of the run.
- **`finally` over per-exit releases.** Synchronous throws from `updateIssueContent`
  and `setGithubIssue`, and a rejected `onIssueLinked`, all sit outside the inner
  try/catch; only a `finally` covers them without stranding a claim.
